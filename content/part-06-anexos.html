Diseño de un sistema — Venta online con reserva de stock

Problema: tienda que despacha de un único depósito; los usuarios eligen producto/variante/cantidad, el sistema reserva temporalmente el stock, valida la cobertura de envío, cobra y emite la orden, evitando vender más unidades de las que hay incluso con muchos usuarios en simultáneo.

1) Esquema de transaccionalidad

El punto crítico es el decremento de stock: debe ser una sección crítica serializada por SKU. Un actor por producto (o un Mutex/lock pesimista por SKU) procesa las reservas de a una → imposible que dos usuarios reserven la última unidad (misma garantía que el invariante de los asientos en Petri). El checkout es una transacción con reserva de TTL: Reservar → ValidarEnvío → Cobrar → Confirmar, y si algún paso falla se hace rollback liberando la reserva.

use actix::prelude::*;

#[derive(Message)]
#[rtype(result = "Result<(), &'static str>")]
struct Reservar { qty: u32 }

struct Producto { stock: u32, reservado: u32 }

impl Actor for Producto { type Context = Context; }

impl Handler for Producto {
    type Result = Result<(), &'static str>;
    fn handle(&mut self, msg: Reservar, _: &mut Context) -> Self::Result {
        // Un mensaje a la vez => decremento serializado, sin sobreventa
        if self.stock - self.reservado >= msg.qty {
            self.reservado += msg.qty;        // reserva temporal (con TTL aparte)
            Ok(())
        } else {
            Err("sin stock")                  // el checkout avisa al usuario
        }
    }
}
// Confirmar: stock -= qty; reservado -= qty.   Liberar: reservado -= qty.

Ej 1 — Sección crítica y corrección

Definir el problema de la sección crítica: programa modelo y especificaciones de corrección

Programa modelo

El programa modelo es el esquema abstracto que describe lo que hace cada proceso en un sistema concurrente que comparte recursos. Se representa como un ciclo infinito cuyo código se divide en dos partes:

  • Parte no-crítica: código que no accede a recursos compartidos.
  • Parte crítica (sección crítica): bloque donde se accede a recursos compartidos.

La sección crítica debe progresar y finalizar eventualmente; un proceso no debe quedarse adentro para siempre.

loop {
            // Parte no-crítica
            seccion_no_critica();

            // Protocolo de entrada (sincronización)
            protocolo_de_entrada();

            // SECCIÓN CRÍTICA (acceso a recurso compartido)
            SECCION_CRITICA();

            // Protocolo de salida (liberación)
            protocolo_de_salida();
        }

Especificaciones de corrección (3 propiedades exigibles)

Una solución al problema de la sección crítica debe cumplir exactamente tres propiedades:

  1. Exclusión mutua (Safety): las instrucciones de la sección crítica no se intercalan. A lo sumo, un proceso se ejecuta dentro de la SC en cualquier momento. Formalmente: no hay dos procesos adentro de la SC simultáneamente.
  2. Ausencia de deadlock (Safety): el sistema nunca entra en un estado donde dos o más procesos se esperan mutuamente y ninguno puede progresar. Específicamente: si dos procesos intentan entrar a la sección crítica, al menos uno de ellos eventualmente lo logra. Más en general: un sistema que aún no finalizó debe poder continuar realizando su tarea productivamente (nunca se traba en espera circular).
  3. Ausencia de starvation (Liveness): si un proceso intenta entrar a la sección crítica, eventualmente debe lograrlo. No existe un proceso que espere indefinidamente mientras otros progresan; todos tienen oportunidad de usar el recurso.
Matiz 1 — Clasificación de deadlock como Safety, no Liveness:

La cátedra clasifica la «ausencia de deadlock» como propiedad de seguridad (Safety), no de vivacidad. Esto difiere de la bibliografía general. La razón: un deadlock es un estado inválido en sí mismo. En el momento en que se forma el ciclo de espera mutua, ya ocurrió algo malo — es terminal, nunca se sale. No es una demora que «eventualmente» se resuelva, sino un error de estado que nunca debió alcanzarse. Por el contrario, starvation sí es liveness: el sistema sigue progresando (otros procesos avanzan), solo un proceso queda postergado indefinidamente.

Matiz 2 — Por qué Fairness NO es especificación de corrección para la SC:

Fairness es una propiedad general sobre todas las instrucciones: si una instrucción está continuamente habilitada, eventualmente debe ejecutarse. Pero la SC no necesita fairness total; solo necesita la garantía más débil y puntual de que un proceso que quiere entrar, eventualmente entra — eso es exactamente ausencia de starvation. Pedir fairness además sería redundante y más fuerte de lo necesario. La especificación de corrección se cubre completamente con las tres propiedades listadas: no se requiere que toda instrucción del sistema sea justa, solo que no haya inanición de procesos en la SC.

Relación con Safety y Liveness

Las propiedades de corrección se clasifican en dos categorías fundamentales:

  • Safety: «algo malo nunca pasa» (debe valer siempre). Incluye exclusión mutua y ausencia de deadlock.
  • Liveness: «algo bueno eventualmente pasa» (debe volverse verdadero en algún momento). Incluye ausencia de starvation.

La dificultad en programación concurrente surge porque la salida puede depender del escenario de ejecución (interleaving), no solo de la entrada. Por eso se necesitan estas propiedades formales: programas secuenciales son determinísticos, pero concurrentes pueden fallar 1 de cada 1000 corridas. Demostrar que las tres propiedades valen en todos los interleavings posibles es lo que garantiza que la solución es correcta.

¿Cuál es la importancia de los criterios de corrección?

En concurrencia se pierde la garantía fundamental de programación secuencial: misma entrada → misma salida. Esto ocurre porque la salida depende del escenario de ejecución — es decir, del interleaving que elige el scheduler entre los threads, que puede variar entre ejecuciones idénticas de entrada. A diferencia del código determinístico, donde debuggear basta para encontrar errores, aquí "anduvo bien en las pruebas" no prueba nada: el programa puede fallar 1 de cada 1000 corridas, sin reproducibilidad. Por eso no alcanza el testing empírico: necesitamos propiedades demostrables para diseñar y validar algoritmos de sincronización.

Se prueban dos clases de propiedades:

Liveness (vivacidad)«Algo bueno eventualmente pasa». Debe volverse verdadera en algún momento, no necesariamente de inmediato.Ausencia de starvation, Fairness

Componentes exactos (criterio de la cátedra):

  • Exclusión mutua (Safety): dos procesos no intercalan ciertas subsecuencias de instrucciones; a lo sumo uno accede a una variable compartida simultáneamente. Protege la integridad de datos.
  • Ausencia de deadlock (Safety, según la cátedra): si dos o más procesos intentan entrar a una sección crítica, al menos uno logra hacerlo eventualmente; un sistema no finalizado siempre puede seguir productivamente. Nota: aunque en bibliografía clásica se clasifica en liveness, la cátedra la ubica en safety.
  • Ausencia de starvation (Liveness): si un proceso está listo para usar un recurso o entrar a una sección crítica, eventualmente lo consigue; ningún proceso queda postergado para siempre mientras otros avanzan.
  • Fairness (Liveness): si una instrucción está continuamente habilitada para ejecutarse, eventualmente aparece en el escenario; el scheduler no puede ignorar indefinidamente un hilo.
Por qué se necesitan LAS DOS: la safety es necesaria pero no suficiente. Un sistema con perfect safety pero sin liveness es un deadlock: correcto pero paralizado. Recíprocamente, un sistema con perfect liveness pero sin safety progresa continuamente pero produce resultados incorrectos (race conditions corrompen datos). Ambas juntas garantizan un sistema que es seguro (no hay corrupción) y progresa (no se cuelga).
Distinción fina: deadlock (safety) ≠ starvation (liveness). En deadlock ningún proceso avanza porque se esperan mutuamente por recursos. En starvation el sistema sí progresa pero un proceso particular queda relegado indefinidamente mientras otros continúan. Ambas son inaceptables pero por razones distintas.

¿Qué es un deadlock y qué consecuencias tiene? ¿Y en distribuido?

Definición de deadlock

Un deadlock (interbloqueo) es una situación en la que dos o más procesos se esperan mutuamente por recursos que cada uno tiene, generando una dependencia cíclica. Ninguno puede avanzar porque cada uno espera algo que el otro posee y nunca liberará.

Ejemplo concreto

Sean dos procesos P1 y P2 que necesitan dos locks, A y B:

  • P1: adquiere lock A, luego intenta adquirir lock B (bloqueado, lo tiene P2).
  • P2: adquiere lock B, luego intenta adquirir lock A (bloqueado, lo tiene P1).

Resultado: ambos quedan indefinidamente esperando un recurso que nunca será liberado.

Consecuencias en un programa concurrente

  • La parte afectada del sistema deja de progresar: los procesos involucrados en el ciclo quedan suspendidos para siempre.
  • Recursos inutilizables: los locks A y B quedan retenidos sin ser liberados, impidiendo que otros procesos los adquieran.
  • Degradación o detención del rendimiento global: si los procesos bloqueados eran críticos (ej. threads de procesamiento), el throughput cae drásticamente o se detiene.
  • Requiere intervención externa: el sistema no puede auto-recuperarse; hay que matar procesos, reiniciar servicios o intervenir manualmente.

Deadlocks en ambientes de concurrencia distribuida

En sistemas distribuidos los deadlocks adquieren complejidades adicionales por la falta de estado global observable y la comunicación por mensajes:

1. No hay estado global observable

En un SO centralizado, el kernel mantiene un grafo de asignación de recursos exacto en todo momento. En distribuido, cada proceso solo conoce su estado local; cualquier información sobre el resto del sistema llega por mensajes con delay y puede estar obsoleta.

2. Mensajes desordenados generan falsos deadlocks

Un coordinador centralizado puede creer erróneamente que existe un ciclo cuando ya se resolvió, o viceversa, porque los mensajes de liberación de recursos llegan fuera de orden. Esto se mitiga con orden causal mediante timestamps de Lamport.

3. Detección requiere protocolos activos
  • Algoritmo centralizado: un coordinador mantiene el grafo global; los procesos le avisan al tomar y liberar recursos. El coordinador busca ciclos regularmente. Ventaja: simple. Desventaja: single point of failure (SPOF).
  • Algoritmo distribuido (Chandy-Misra-Haas): cuando un proceso se bloquea, envía un probe message (indicando el proceso bloqueado, el emisor y el destinatario) al que tiene el recurso. Éste lo reenvía a los procesos de los que él espera. Si el probe vuelve al origen, existe un ciclo. Ventaja: sin SPOF. Desventaja: más mensajes, latencia y complejidad.
4. Resolución vía prevención con timestamps (no elegir víctima local)

En lugar del enfoque centralizado de elegir qué proceso abortar, los sistemas distribuidos usan timestamps globales de Lamport para ordenar las transacciones y tomar decisiones consistentes en todos los nodos:

AlgoritmoEl que pide es MÁS VIEJOEl que pide es MÁS JOVEN
Wait-DieEspera (conserva el recurso al más antiguo)Aborta (muere) y reintenta después
Wound-WaitAborta (hiere) al que tiene el recurso, recuperándoloEspera (respeta al proceso más antiguo)

Ambos algoritmos evitan espera circular porque nunca permiten que un proceso viejo espere a uno joven — se impone un orden temporal que previene ciclos (satisface la condición de Coffman).

Impacto práctico
  • Costo de comunicación real: la detección y resolución implican múltiples rondas de mensajes por la red, no solo lectura de memoria local.
  • Ambigüedad por fallas parciales: un proceso que no responde puede estar muerto, haber perdido el mensaje, o estar lento. El sistema no puede distinguir estos casos con certeza.
  • Trade-off centralizado vs distribuido: un coordinador centralizado es simple pero frágil; un sistema distribuido es resiliente pero costoso en comunicación y complejidad.
Matiz de cátedra (para no perder puntos): el deadlock rompe SAFETY, no liveness. Un deadlock es un estado inválido terminal en sí mismo (el sistema entra en una configuración de la que nunca puede salir), no algo que "eventualmente debería suceder y se retrasa" (eso sería liveness). Contraste: la starvation es un problema de liveness — el sistema global progresa, pero un proceso queda indefinidamente postergado sin motivo válido.

Mecanismos de prevención de deadlocks en distribuido (a detalle)

Contexto: timestamp único y global

Cada transacción recibe un timestamp único y global (usando el algoritmo de Lamport, donde cada evento se marca con un número que crece monotónicamente en el sistema) al iniciar. Este timestamp determina el orden lógico de las transacciones: un timestamp más bajo significa una transacción «más vieja» (inició antes). Cuando un proceso se bloquea esperando un recurso que otro proceso tiene, ambos comparan sus timestamps para decidir quién espera y quién aborta, evitando así la espera circular.

Algoritmo Wait-Die

Regla: el que pide el recurso compara su timestamp con el del que lo sostiene:

  • Si el que pide es más viejo (timestamp menor): espera pacientemente.
  • Si el que pide es más joven (timestamp mayor): aborta su transacción («muere») y la reintenta más tarde con un nuevo timestamp.

Por qué previene deadlock: este algoritmo impide que una transacción más joven espere por una más vieja. Dado que cada proceso solo puede esperar a uno más viejo, no es posible formar un ciclo de espera circular (si P1 espera a P2, entonces P1 es más viejo que P2; si P2 esperara a P1, sería más viejo, contradicción). De esta forma, rompe la condición de espera circular de Coffman mediante un orden total basado en timestamps.

Naturaleza: no-preemptive — nadie es abortado contra su voluntad; solo se aborta quien intenta pedir (y es más joven).

Costo: transacciones jóvenes pueden abortar frecuentemente, generando rollbacks y reintentos. En sistemas con alta actividad de escritura, esto puede acumular muchos aborts.

Algoritmo Wound-Wait

Regla: el que pide el recurso compara su timestamp con el del que lo sostiene:

  • Si el que pide es más viejo (timestamp menor): aborta («hiere») al que tiene el recurso, tomándolo para sí.
  • Si el que pide es más joven (timestamp mayor): espera pacientemente.

Por qué previene deadlock: este algoritmo impide que transacciones más jóvenes bloqueen a las más viejas. Invierte la dirección de la espera respecto a Wait-Die: si P1 (más viejo) necesita un recurso de P2 (más joven), P1 lo arrebata; si P2 necesita algo de P1, P2 espera. Nuevamente, no hay ciclo posible porque la dirección está forzada por el orden de timestamps.

Naturaleza: preemptive — una transacción puede ser abortada por orden de otra (la más vieja desaloja a la más joven).

Costo: transacciones viejas tienen prioridad absoluta, reduciendo sus aborts. Sin embargo, una transacción vieja puede hacer abortar varias más jóvenes. Generalmente tiene menor número de aborts y rollbacks que Wait-Die, porque las transacciones largas/importantes (viejas) se protegen y progresan sin reintentos.

Rompen la condición de espera circular de Coffman

Los cuatro requisitos para que exista un deadlock (condiciones de Coffman) son: exclusión mutua, espera y retención, no apropiación, y espera circular. Ambos algoritmos rompen la espera circular al imponer un orden global basado en timestamps: en lugar de permitir ciclos arbitrarios (P1→recurso-A→P2→recurso-B→P1), solo permiten esperas que respetan el orden temporal. Una transacción no puede esperar indefinidamente en una cadena que vuelve a ella porque los timestamps son estrictamente ordenados y acíclicos.

Matiz: no confundir con exclusión mutua distribuida

Prevención de deadlock vs. exclusión mutua distribuida — son problemas distintos:
• Exclusión mutua distribuida (centralizado, Ricart-Agrawala, Token Ring): garantiza que un solo proceso a la vez entre a la sección crítica sobre un recurso puntual.
• Prevención de deadlock (Wait-Die, Wound-Wait): evita ciclos cuando hay múltiples recursos y cada proceso puede pedir varios en orden. Son complementarios: el mutex distribuido protege un recurso individual; la prevención de deadlock evita que el uso coordinado de varios mutex se trabe en un ciclo global.

Comparación con detección

Un tercer enfoque (no prevención, sino detección) existe en sistemas distribuidos: usar probe messages (Chandy-Misra-Haas) para detectar un ciclo después de que se forma, y luego romperlo abortando una transacción. [Parcial] Identificar la estructura y sus errores (Mutex + Condvar)

Consigna: dado un struct { mutex: Mutex<i32>, cond_var: Condvar } con function_1 (si amount <= 0 hace wait, luego -= 1) y function_2 (+= 1 y notify_all): ¿qué estructura de sincronización es y qué error tiene?

Resolución

Qué es: un semáforo contador implementado como monitor (mutex + variable de condición). Sus dos variables internas se leen directo del código: mutex: Mutex<i32> es el contador V (recursos disponibles, no negativo) y la cola interna de la Condvar es el conjunto L de procesos bloqueados. function_1 es el wait() («obtener acceso») y function_2 es el signal() («liberar»).

Error 1 (el grave): usa if *amount <= 0 { wait } en vez de while. Condvar::wait() en Rust puede retornar aunque nadie haya hecho notify (spurious wakeup), y además notify_all despierta a varios waiters que compiten por el mismo recurso. Con if, el proceso chequea la condición una sola vez: si despierta con amount == 0 sigue de largo y hace *amount -= 1, rompiendo la invariante del semáforo (V ≥ 0) y dejando el contador en negativo. Solución: cambiar el if por while, para revalidar la condición en cada despertar.

Error 2 (el detalle que suma): notify_all() en function_2. Se incrementó en 1 solo recurso, así que solo un thread va a poder tomarlo: despertar a todos genera una estampida en la que N−1 revalidan la condición y se vuelven a dormir (trabajo desperdiciado y contención por el mutex). Corresponde notify_one(). Ojo: notify_all sí es necesario cuando los waiters esperan por condiciones distintas sobre la misma condvar.

Comparar los efectos negativos: deadlock, race condition, starvation y busy-wait

La corrección de un programa concurrente se demuestra sobre dos clases de propiedades: safety («algo malo nunca pasa») y liveness («algo bueno eventualmente pasa»). Los cuatro efectos negativos se distribuyen entre estas propiedades:

Efecto Qué es Propiedad que rompe Efecto en el programa Cómo se corrige
Deadlock Un conjunto de procesos queda bloqueado indefinidamente, cada uno esperando un recurso que otro del conjunto posee (A espera el recurso 2 teniendo el 1; B espera el 1 teniendo el 2). Safety (ausencia de deadlock es propiedad de seguridad) El sistema se congela, la ejecución se detiene de forma terminal. Si es crítico, parece como si se hubiera colgado. Romper una condición de Coffman: ordenar la toma de recursos, permitir preemption, o no permitir hold-and-wait.
Race condition Dos o más procesos acceden a estado compartido sin sincronización adecuada y el resultado depende del orden (timing) de ejecución. Safety (exclusión mutua) Bug intermitente no reproducible; datos corruptos, resultados incorrectos que varían según el interleaving. Difícil de detectar en testing. Serializar el acceso al estado compartido: usar lock, semáforo, actor, o condvar para garantizar exclusión mutua.
Starvation Un proceso listo y esperando un recurso nunca lo obtiene porque otros lo acaparan indefinidamente, aunque el sistema en general sigue progresando. Liveness (ausencia de starvation) Injusticia: un proceso particular queda postergado para siempre, pierde fairness, aunque los demás avanzan normalmente. Implementar política fair (FIFO, envejecimiento, timestamps como en wait-die/wound-wait) que ordene el acceso por antigüedad.
Busy-wait Un hilo gira en un loop chequeando una condición para poder avanzar, consumiendo CPU sin hacer trabajo útil. Ninguna propiedad de corrección (es problema de eficiencia) Mal uso de CPU que degrada el rendimiento de otros procesos, aunque la lógica de sincronización sea correcta. Desperdicio energético. Reemplazar el spin por bloqueo real (semáforo, condition variable, park) para ceder CPU al SO.
  • Deadlock:
    • Definición: situación en la que un conjunto de procesos queda bloqueado indefinidamente porque cada uno espera un recurso que otro del conjunto tiene. Requiere que se cumplan simultáneamente las cuatro condiciones de Coffman: exclusión mutua, hold-and-wait, no-preemption y espera circular.
    • Causa / mecanismo: cuando hay múltiples recursos y los procesos los adquieren sin un orden coordinado, pueden formar ciclos de espera. Por ejemplo, P1 toma recurso A y espera B; P2 toma B y espera A.
    • Efecto concreto: el programa se congela completamente en ese punto. Ninguno de los procesos involucrados progresa nunca más. Si estos procesos son críticos para el sistema, el resultado es un sistema aparentemente "muerto" o colgado.
    • Corrección: impedir deadlock rompiendo una de las cuatro condiciones de Coffman. En la práctica, lo más común es impedir espera circular ordenando la adquisición de recursos (si siempre pides A antes que B) o usando algoritmos distribuidos como wait-die (el más viejo espera, el más joven aborta y reintenta).
  • Race condition:
    • Definición: el resultado de la ejecución depende del orden en que se intercalen las instrucciones de múltiples procesos que acceden a estado compartido sin sincronización.
    • Causa / mecanismo: falta de exclusión mutua. Dos procesos leen, modifican y escriben la misma variable sin coordinarse. Entre la lectura y la escritura de uno, el otro puede haber modificado el valor. Ejemplo clásico: dos threads incrementan un contador sin lock; ambos leen 5, incrementan a 6, y escriben 6 — el resultado es 6 en lugar de 7.
    • Efecto concreto: bug no determinista. El programa puede funcionar correctamente en una corrida (si el timing es favorable) y fallar en otra (si el timing es adverso). Datos corruptos, cálculos incorrectos, inconsistencia de invariantes. Muy difícil de reproducir y debuguear.
    • Corrección: usar un mecanismo de sincronización que garantice exclusión mutua: lock, semáforo binario, condvar, o modelo de actores (que serializa el acceso por diseño). La sección crítica debe ser lo más pequeña posible.
  • Starvation (inanición):
    • Definición: un proceso que está listo y esperando acceso a un recurso nunca lo obtiene porque otros procesos lo acaparan indefinidamente, aunque el sistema global sigue avanzando.
    • Causa / mecanismo: política de scheduling injusta o no-fair. Ejemplo: si hay una cola de procesos esperando un lock pero el scheduler no respeta FIFO, procesos nuevos pueden «colarse» y tomar el lock antes que los que ya estaban esperando. O en sistemas distribuidos, el proceso más joven puede ser expropiado siempre por el más viejo (wound-wait).
    • Efecto concreto: ese proceso en particular nunca progresa, aunque otros sí. Falta de fairness. En sistemas de tiempo real o de justicia (p. ej. un servidor web), significa que ciertos clientes quedan sin servir indefinidamente.
    • Corrección: implementar una política fair: colas FIFO (el primero en llegar es el primero en servirse), envejecimiento (dar prioridad a procesos que llevan más tiempo esperando), o timestamps (wait-die: el más viejo espera; wound-wait: el más joven se aborta).
  • Busy-wait (espera activa):
    • Definición: un hilo gira continuamente en un loop chequeando una condición (p. ej. while !condition { } o con sleep), consumiendo CPU sin hacer trabajo útil, solo esperando a que algo externo cambie el estado.
    • Causa / mecanismo: usar polling (preguntar repetidamente) en lugar de bloquearse en un mecanismo que el SO controle (semáforo, condvar). El hilo no se duerme realmente; solo cede CPU brevemente (si hay sleep) y vuelve a chequear.
    • Efecto concreto: uso excesivo de CPU. El hilo consume ciclos de procesador sin hacer trabajo útil, degradando el rendimiento de otros procesos y aumentando el consumo de energía. Sin embargo, la lógica puede ser correcta: si la condición se cumple, el programa avanza (así sea ineficientemente).
    • Corrección: bloquearse en lugar de hacer polling. Usar un semáforo (para una condición binaria), una condition variable (para condiciones más complejas), u otro mecanismo que el SO controle. El SO despierta el hilo solo cuando ocurre el evento, sin que el hilo gaste ciclos chequeando.
Matiz para no perder puntos: deadlock vs starvation. En deadlock, nadie de los procesos involucrados progresa nunca — es un estado terminal que rompe safety (la ausencia de deadlock es una propiedad de seguridad: nunca debe alcanzarse ese estado). En starvation, el sistema en general sí progresa — otros procesos avanzan normalmente — pero un proceso puntual queda postergado indefinidamente, violando liveness (ausencia de starvation: todo proceso que está listo debe eventualmente obtener el recurso).
Otro matiz importante: busy-wait no rompe corrección. Un programa con busy-wait puede ser completamente correcto (exclusión mutua garantizada, sin deadlock, sin race conditions) pero ser muy ineficiente (quema CPU innecesariamente). Es un problema de eficiencia y recursos, no de corrección. Sin embargo, la ineficiencia puede ser tan severa que degradue a otros procesos, por eso se considera un efecto negativo que debe evitarse.

Las 4 condiciones de Coffman para que ocurra un deadlock

Un deadlock es posible solo si se cumplen simultáneamente las cuatro condiciones de Coffman. Romper una sola alcanza para prevenirlo:

Condición Definición precisa Estrategia para romperla Viabilidad práctica
Exclusión mutua Un recurso solo puede estar en poder de un proceso a la vez. Permitir que múltiples procesos usen el recurso simultáneamente (ej. lock de lectura compartido). No siempre viable: algunos recursos (archivo en escritura, transacción crítica) requieren exclusión mutua.
Espera y retención
(Hold and Wait)		 Un proceso retiene recursos mientras espera obtener otros adicionales. Pedir todos los recursos necesarios de una vez, antes de empezar; si no hay, no tomar ninguno. Viable pero restrictiva: obliga a conocer de antemano qué recursos se usarán y aumenta contención.
No apropiación
(No Preemption)		 Un recurso no puede ser arrebatado por la fuerza; solo se libera voluntariamente. Permitir que el sistema le quite (preempt) un recurso a un proceso (ej. desalojar).. Viable en algunos contextos (CPU), muy difícil en otros (I/O persistente, transacciones parciales).
Espera circular
(Circular Wait)		 Existe un ciclo P1→P2→...→Pn→P1 donde cada uno espera un recurso que tiene el siguiente. Imponer un orden total de adquisición (ej. siempre pedir A antes que B); o usar timestamps para decidir quién espera/aborta. Más usada en la práctica: fácil de implementar sin sacrificar mucho rendimiento.

Prevención en sistemas distribuidos: wait-die y wound-wait

En sistemas distribuidos, romper la espera circular usando orden de timestamps es la estrategia preferida. Cada transacción recibe un timestamp único (Lamport) al iniciar. Cuando un proceso se bloquea por un recurso que otro tiene, se comparan timestamps (más chico = más «viejo»):

  • Wait-Die: si el que pide es más viejo que el que tiene el recurso, espera; si es más joven, aborta (die) y reintenta. Mnemónico: «vieja espera, joven muere».
  • Wound-Wait: si el que pide es más viejo, fuerza el abort (wound) del que tiene el recurso; si es más joven, espera. Mnemónico: «vieja hiriente, joven paciente».

Ambos algoritmos rompen la espera circular porque solo se permite esperar en una dirección del orden temporal — el viejo nunca espera al joven —, garantizando una ordenación global que previene ciclos.

Matiz clave (para no perder puntos): romper exclusión mutua frecuentemente no es posible porque hay recursos que intrínsecamente requieren acceso exclusivo (un dato siendo escrito, un archivo en transacción crítica). La mayoría de sistemas confían en romper la espera circular mediante orden de recursos o timestamps, que es la más viable: fácil de implementar (define un orden fijo de adquisición o usa timestamps del sistema) y tolerable en carga típica sin degradar performance significativamente.

¿Qué es un semáforo? Operaciones y variables internas

Mecanismo de sincronización con dos variables internas: un entero no negativo V (contador de recursos disponibles, inicialmente k ≥ 0) y un conjunto/cola L de procesos bloqueados (inicialmente vacío). Modela N recursos idénticos accesibles a varios procesos concurrentemente. Ofrece dos operaciones atómicas (garantizadas por el SO):

  • wait(S) / P(S) / acquire: Si V > 0, decrementa V en 1 y el proceso continúa. Si V == 0, el proceso se bloquea y se agrega a L (el contador nunca queda negativo).
  • signal(S) / V(S) / release: Si L está vacío, incrementa V en 1. Si no, despierta a un proceso arbitrario de L (sin orden FIFO garantizado) y lo pone en estado ready (no incrementa V en este caso).

Pseudocódigo crudo:

// Semáforo: dos operaciones atómicas
        // Variables internas: V (int >= 0), L (conjunto de procesos bloqueados)

        fn wait(sem: &mut Semaphore) {
            if sem.V > 0 {
        sem.V -= 1;
            } else {
        // agregar proceso actual a L y bloquearse
        sem.L.push(current_process());
        block();
            }
        }

        fn signal(sem: &mut Semaphore) {
            if sem.L.is_empty() {
        sem.V += 1;
            } else {
        // despierta UN proceso arbitrario de L (no el primero necesariamente)
        let proc = sem.L.remove_arbitrary();
        ready(proc);
            }
        }

Variantes según V inicial:

  • Semáforo binario (V = 1): Solo permite un proceso a la vez; se comporta como un mutex. Evita race conditions en secciones críticas.
  • Semáforo contador (V = N): Permite a lo sumo N procesos accediendo simultáneamente (N recursos, ej. N conexiones de un pool, N lugares de estacionamiento).

Invariantes: V ≥ 0 siempre; V = k + #signal(S) − #wait(S) (donde k es el valor inicial).

Matiz crítico (para no perder puntos): signal despierta a un proceso arbitrario de L (el SO elige sin garantía de orden FIFO). Esto hace que un semáforo por sí solo NO garantiza ausencia de starvation; puede haber procesos que esperen indefinidamente mientras otros son despertados. Contrasta con signalC en monitores, que despierta al del tope del FIFO (orden determinista). Para starvation-freedom, hace falta implementación fair (como lectores-escritores con cola de turnos, §13).

¿Qué es un mutex? Operaciones y diferencia con el semáforo

Definición: Mutex en Rust

Mutex (en Rust: std::sync::Mutex<T>) garantiza exclusión mutua entre hilos: solo un thread a la vez accede a la sección crítica. A diferencia del semáforo, tiene noción de dueño: envuelve el dato compartido y solo quien hizo lock() puede hacer unlock().

Operaciones básicas

  • lock(): el hilo se bloquea hasta poder obtener el mutex, devuelve un MutexGuard<T>.
  • unlock() (o drop() del guard): libera el mutex. En Rust, ocurre automáticamente al salir del scope (patrón RAII).
  • Requieren soporte de hardware y sistema operativo (instrucciones atómicas tipo test-and-set).

Detalles de Rust

Mutex<T> envuelve el dato (no es un lock suelto al lado); .lock() devuelve un MutexGuard<T> que se libera por RAII al salir del scope o con drop() explícito. Crucialmente, MutexGuard<T> no implementa Send: el compilador impide pasarlo a otro hilo para que lo libere — solo el mismo hilo que hizo lock() puede liberarlo. El patrón para mutar estado compartido entre hilos es Arc<Mutex<T>> (compartir + serializar).

Un mutex puede quedar envenenado (poisoned) si un hilo que lo tomó hace panic!() mientras lo tiene: las llamadas posteriores a lock() devuelven Err. Por eso casi siempre ves .lock().unwrap() — estás propagando ese posible envenenamiento.

Comparación: Mutex vs Semáforo binario

La diferencia clave

NO es "qué hacen", sino "quién puede operar":

El mutex está pensado como propiedad de un mismo hilo — una llave que me llevo y devuelvo yo mismo. Solo quien tomó el lock puede liberarlo; el compilador lo enforza a través del tipo MutexGuard<T> que no es Send.

El semáforo es una herramienta de sincronización entre hilos distintos. Uno hace wait() (se bloquea), otro hace signal() que lo despierta — no hay noción de "dueño". signal() no necesita ningún "comprobante" previo: cualquier hilo puede llamarlo, haya hecho wait() o no.

Por eso el semáforo es la herramienta natural para productor-consumidor: el consumidor espera y es el productor (hilo distinto) quien lo despierta. En Rust, Mutex<T> + Condvar es cómo se construye un semáforo "a mano".

¿No son intercambiables un mutex binario y un semáforo?

No. Aunque los dos dan exclusión mutua, son distintos:

  • lock()/drop(): se libera un objeto nominal que te entregaron a vos (MutexGuard). Solo quien lo tiene puede liberarlo.
  • wait()/signal(): operaciones independientes sobre un contador compartido. signal() es una operación libre — cualquier hilo puede hacerla, haya hecho wait() o no.

Un mutex de un hilo A no protege la misma sección si B no coopera; un semáforo sí porque es una barrera de recursos. En productor-consumidor, necesitás que el productor pueda "despertar" al consumidor sin que el consumidor lo "dueño" primero — eso es signal(), no drop().

En el final: diferenciá qué datos comparten (mutex envuelve el dato; semáforo es abstracto), quién puede liberar (solo dueño vs cualquiera), y por qué productor-consumidor usa semáforo (comunicación entre hilos distintos, no protección de un objeto puntual). Mencioná que MutexGuard no es Send — eso es donde Rust enforza la noción de dueño a nivel de tipos. Ver §11.

¿Qué es una barrera y qué operación tiene?

Una barrera (std::sync::Barrier) es un mecanismo de sincronización que obliga a un conjunto de N procesos/threads a esperar en un punto específico del cómputo hasta que todos hayan llegado. Ninguno continúa hasta que llegan todos. La operación es esencialmente una sola: wait().

Mecanismo

Cada thread que alcanza la barrera ejecuta wait(). Si todavía no llegaron todos, queda bloqueado. Cuando el último thread alcanza la barrera, se liberan simultáneamente todos los bloqueados y continúan su ejecución. Las barreras de Rust son reutilizables automáticamente: tras liberar a todos, la barrera se reinicia para la siguiente fase.

Concepto de líder en Rust

En std::sync::Barrier, BarrierWaitResult::is_leader() devuelve true solo para el último hilo que llega (el «líder») y false para el resto. Por qué tiene sentido: todos los hilos quedan bloqueados hasta que llega el último. Ese último hilo es el único que, en el momento de su llegada, ya sabe con certeza que la condición de desbloqueo se cumplió, porque su propia llegada la completa. Sirve para que exactamente un hilo haga una acción puntual tras la sincronización (loguear, consolidar resultado) sin necesidad de sincronización extra.

Uso clásico: sincronización por fases

Una barrera asegura que todos terminen una etapa antes de que cualquiera avance a la siguiente. El requisito clave es que el trabajo se divida en rondas/fases bien definidas, donde una fase depende de que la anterior haya sido completada por todas las subtareas. Ejemplos reales:

  • Simulaciones por pasos (física, juegos): cada paso de tiempo necesita que todos los agentes actualicen su estado antes de calcular el siguiente frame.
  • Algoritmos paralelos por fases: multiplicación de matrices por bloques, donde cada bloque depende de que otros bloques terminen su cálculo.
  • Motores de videojuegos: renderizado, física e IA sincronizados por frame — cada subsistema debe terminar su fase antes de que comience el siguiente.
  • Problema del banquero (cátedra): dos barreras — una para «todos listos para iniciar la semana» antes de repartir dinero, otra para «todos calcularon su parte» antes de permitir retiros.

Implementación en Rust

// Barrera: los N threads se esperan mutuamente en un punto antes de seguir

Cuándo NO conviene

En tareas con latencias muy variables e impredecibles (llamadas a APIs externas, I/O de red), usar barreras es mala idea porque obliga a esperar al más lento sin necesidad conceptual real. Ahí conviene un modelo async/reactivo, donde cada tarea avanza cuando está lista, sin forzar sincronización global.

Matiz para no perder puntos: no confundir el «líder» de una barrera con el líder de los algoritmos distribuidos (Bully, Ring). El líder de la barrera se redetermina en cada ciclo (es el último en llegar a esa ronda) y no tiene ninguna responsabilidad más allá de la etiqueta. El líder distribuido tiene rol activo y persistente (coordina, mantiene estado, se reelige si cae). Son conceptos distintos aunque compartan nombre.

¿Qué es un monitor? Operaciones y de qué se compone

Un monitor es una herramienta de sincronización que encapsula datos + procedimientos + exclusión mutua implícita. Su característica central: solo un proceso ejecuta un procedimiento del monitor a la vez (la exclusión mutua es responsabilidad de la estructura, no del programador — no hay que escribir código de locks).

Componentes de un monitor

Siempre están estos elementos (todos obligatorios):

  • Nombre del monitor (ej. Buffer, Impresora).
  • Variables internas protegidas: el estado compartido que el monitor cuida (ej. el contenido del buffer, el número de ítems, si está lleno).
  • Procedimientos públicos: interfaz del monitor, los métodos que otros procesos llaman. Cada uno es una entrada "guardada" — solo uno ejecuta a la vez. Ej. insertar(), extraer().
  • Variables de condición (condvars): no guardan valor, solo mantienen un FIFO de procesos bloqueados. Ej. notEmpty, notFull.
  • Inicialización: estado inicial de las variables internas.

Operaciones atómicas sobre variables de condición

OperaciónSemántica
waitC(cond)SIEMPRE bloquea al proceso, lo agrega al FIFO de la condición y libera el lock del monitor (otro puede entrar).
signalC(cond)Despierta al proceso del tope del FIFO de la condición; si la cola está vacía, no hace nada.
empty(cond)Devuelve true si el FIFO de la condición está vacío.

Ejemplo: buffer acotado (estructura completa)

// MONITOR Buffer
        // Componentes: nombre (Buffer), variables internas (items, size, in_idx, out_idx),
        //              procedimientos públicos (insert, extract), condvars (notFull, notEmpty),
        //              inicialización

        struct Buffer {
            // Variables internas (protegidas por la exclusión mutua del monitor)
            items: Vec,
            size: usize,
            in_idx: usize,
            out_idx: usize,
            count: usize,  // cuántos elementos hay ahora
        }

        struct MonitorBuffer {
            // En Rust, Mutex implementa la exclusión mutua implícita
            data: Mutex,
            // Variables de condición (cada una es un FIFO separado)
            not_full: Condvar,   // esperar a que NO esté lleno
            not_empty: Condvar,  // esperar a que NO esté vacío
        }

        impl MonitorBuffer {
            // INICIALIZACIÓN
            fn new(size: usize) -> Self {
        MonitorBuffer {
            data: Mutex::new(Buffer {
                items: vec![0; size],
                size,
                in_idx: 0,
                out_idx: 0,
                count: 0,
            }),
            not_full: Condvar::new(),
            not_empty: Condvar::new(),
        }
            }

            // PROCEDIMIENTO 1: insertar
            fn insert(&self, x: i32) {
        let mut buf = self.data.lock().unwrap();  // AQUÍ entra con exclusión mutua

        // Evaluamos la condición ANTES de esperar, en un WHILE (no if)
        // por spurious wakeup (el monitor puede despertarte sin causa)
        while buf.count == buf.size {              // mientras esté lleno
            buf = self.not_full.wait(buf).unwrap(); // waitC: bloquea y libera el lock
        }

        // Ahora hay espacio: insertamos
        buf.items[buf.in_idx] = x;
        buf.in_idx = (buf.in_idx + 1) % buf.size;
        buf.count += 1;

        // Despertamos a quien espere por NOT_EMPTY
        self.not_empty.notify_one();  // signalC: despierta al tope del FIFO de not_empty
            }  // FIN procedimiento: lock se libera automáticamente

            // PROCEDIMIENTO 2: extraer
            fn extract(&self) -> i32 {
        let mut buf = self.data.lock().unwrap();  // AQUÍ entra con exclusión mutua

        while buf.count == 0 {                     // mientras esté vacío
            buf = self.not_empty.wait(buf).unwrap(); // waitC: bloquea y libera el lock
        }

        // Ahora hay elementos: extraemos
        let x = buf.items[buf.out_idx];
        buf.out_idx = (buf.out_idx + 1) % buf.size;
        buf.count -= 1;

        self.not_full.notify_one();  // signalC: despierta a quien espere NOT_FULL

        x
            }  // FIN procedimiento: lock se libera automáticamente
        }

Semáforo vs Monitor: similitudes, diferencias y cuándo usar cada uno

Definición breve: un semáforo es un contador entero no negativo con dos operaciones atómicas (wait/signal) que actúa como guarda de acceso a recursos; un monitor es una estructura que combina exclusión mutua implícita (solo un proceso ejecuta un procedimiento a la vez) con variables de condición (FIFO de espera sin valor propio) para sincronizar acceso a estado protegido.

Tabla comparativa: operaciones wait/signal vs waitC/signalC

Aspecto Semáforo (wait/signal) Monitor (waitC/signalC)
¿wait bloquea? Puede o no (si V > 0 no bloquea, decrementa y sigue) waitC siempre bloquea y libera el monitor
¿signal tiene efecto? signal siempre tiene efecto: incrementa o despierta un proceso signalC no tiene efecto si la cola está vacía
¿A quién despierta? Un proceso arbitrario de los bloqueados (sin orden) El del tope del FIFO (orden de llegada)
Tras la señal El desbloqueado puede continuar inmediatamente El desbloqueado espera a que el señalizador deje el monitor

Diferencia fundamental: exclusión mutua explícita vs implícita

  • Semáforo: el programador debe colocar wait/signal en el orden correcto. La garantía de exclusión mutua es responsabilidad del código. Si se olvida un signal o se invierten las operaciones, se pierde la protección.
  • Monitor: la exclusión mutua está incorporada en la estructura. El compilador/runtime impone que solo un proceso ejecute un procedimiento del monitor a la vez. El programador no puede olvidarlo.

Diferencia: estado asociado y encapsulación

  • Semáforo: es un contador abstracto sin estado protegido asociado. Representa "cantidad de recursos disponibles" pero no qué datos hay detrás; el programador debe manejar por separado buffers, flags, etc., (típicamente con un mutex adicional). El semáforo y los datos protegidos viven en lugares distintos.
  • Monitor: encapsula juntos las variables internas protegidas y los procedimientos que las acceden. La estructura une el estado con su protocolo de acceso. Esto reduce errores: no se puede acceder a los datos sin pasar por los procedimientos del monitor.

Diferencia: qué errores habilita cada uno

  • Semáforo:
    • Olvidarse un signal → procesos quedan bloqueados para siempre (deadlock).
    • Invertir el orden wait/signal o usarlos en la sección equivocada → se pierden garantías de exclusión mutua (race condition).
    • No elegir bien los valores iniciales de los semáforos → comportamiento incorrecto desde el inicio.
  • Monitor:
    • Esos tres errores arriba no son expresables: no se puede olvidar un signalC o invertir el orden porque la sintaxis del monitor lo evita.
    • El error típico es la condición del while en la variable de condición: si la condición es incorrecta, el monitor espera/despierta en momentos equivocados. Por eso la regla es siempre while, nunca if (evita spurious wakeup).

Similitudes

  • Ambos evitan busy-wait: el proceso se bloquea pasivamente y el SO no le cede CPU hasta que se cumpla la condición.
  • Ambos serializan acceso a recursos compartidos: garantizan que, en un momento dado, solo un proceso (o grupo controlado) toca los datos.
  • Ambos tienen garantías atomicidad de sus operaciones: es imposible que dos procesos ejecuten wait/signal simultáneamente.
  • Implementabilidad mutua: un semáforo se puede construir como monitor (con Mutex<i32> + Condvar), y un monitor se puede emular con semáforos (aunque más laboriosamente).

Cuándo usar cada uno

  • Monitor: cuando el recurso es complejo con múltiples condiciones de sincronización (ej.: cola de impresión con notFull/notEmpty, buffer de datos con estados internos, servidor con clientes que esperan turnos). La encapsulación del estado protege contra errores.
  • Semáforo: cuando solo hay que contar accesos a N recursos idénticos (ej.: N impresoras, M conexiones de BD, K lugares de estacionamiento). El código es simple: acquire antes de entrar, release después; no hay estado complicado. También en productor-consumidor infinito con un solo semáforo notEmpty.

  • Definir cada estructura (no asumir que el lector sabe qué es).

Productor-consumidor con semáforos

Esqueleto (Ben-Ari, 1 productor y 1 consumidor)

La solución clásica usa dos semáforos de conteo: notFull (contador de espacios libres en el buffer) inicializado en N (capacidad), y notEmpty (contador de ítems disponibles) inicializado en 0.

let not_full  = Semaphore::new(N);     // huecos libres (capacidad del buffer)
        let not_empty = Semaphore::new(0);    // ítems disponibles
        let buffer    = Mutex::new(VecDeque::new());

        // Productor
        loop {
            let item = producir();
            not_full.acquire();                        // espera si el buffer está lleno
            buffer.lock().unwrap().push_back(item);    // acceso exclusivo al buffer
            not_empty.release();                       // avisa: hay un ítem disponible
        }

        // Consumidor
        loop {
            not_empty.acquire();                       // espera si el buffer está vacío
            let item = buffer.lock().unwrap().pop_front().unwrap();
            not_full.release();                        // avisa: se liberó un espacio
            consumir(item);
        }

Sincronización vs Exclusión Mutua: la distinción crítica

Los semáforos notFull y notEmpty resuelven la sincronización productor↔consumidor: coordinan cuándo producir (hay espacio) y cuándo consumir (hay elementos). Pero no garantizan exclusión mutua dentro de cada familia.

  • Con 1 productor y 1 consumidor: el mutex del buffer es innecesario. No hay competencia: el productor siempre opera sobre una posición que el consumidor nunca toca, y viceversa. Es la solución de Ben-Ari: dos semáforos bastan.
  • Con múltiples productores y/o consumidores: se agrega un mutex (o semáforo binario) que envuelve específicamente el acceso al buffer — es decir, el push/pop físico. Sin él, dos productores podrían escribir simultáneamente, o dos consumidores podrían leer la misma posición → race condition.

Resumen: semáforo de conteo → coordinación (¿hay espacio? ¿hay elementos?); mutex → exclusión mutua (protege la estructura compartida). Con varios productores y/o consumidores se necesitan ambas.

Por qué el semáforo es la herramienta natural

El semáforo modela naturalmente esta situación porque el que hace wait(notFull) es un hilo distinto del que hace signal(notFull): es el consumidor quien retorna espacio para que el productor continúe. Un mutex no sirve para esto (solo lo libera quien lo tomó); la variable de condición tampoco es la primera opción porque aquí no se "espera por una condición que el mismo proceso chequea", sino que se espera que otro proceso haga trabajo que genere la condición.

Error clásico de parcial: tomar el mutex del buffer antes de hacer wait(not_full). Así: buffer.lock(); not_full.acquire(); → el hilo se bloquea esperando espacio teniendo el buffer tomado → el otro hilo no puede ni siquiera hacer pop para liberar espacio → deadlock. Siempre: semáforo primero, mutex después.

Matiz: buffer acotado vs infinito

Un buffer acotado (con capacidad N) exige dos semáforos. Si se omite notFull y se deja solo notEmpty, lo que está modelado es en realidad un buffer infinito — nunca se pregunta "¿hay espacio?", así que el buffer crece sin límite. Ese es el error que comete un código que solo usa wait(notEmpty) en el consumidor y signal(notEmpty) en el productor: resuelve sincronización de consumo, pero no acota el tamaño.

Locks en Unix vs Rust, tipos y «lock envenenado»

Un lock (cerradura) implementa exclusión mutua: una variable de estado con dos operaciones, lock() (el proceso se bloquea hasta poder tomarlo) y unlock() (lo libera). No se puede construir en software puro: requiere soporte de hardware y del sistema operativo, típicamente una instrucción atómica del tipo test-and-set, porque el «fijarse si está libre y tomarlo» tiene que ser un único paso indivisible.

Los dos tipos son los mismos en los dos mundos:

  • Compartido / shared (lectura): varios procesos o threads pueden tenerlo simultáneamente. Sirve porque leer no rompe invariantes.
  • Exclusivo / exclusive (escritura): uno solo a la vez, y bloquea a todos los demás (lectores incluidos).

La regla de compatibilidad: para tomar un shared hay que esperar a que se liberen todos los exclusive; para tomar un exclusive, que se liberen todos, de los dos tipos.

Locks en Unix

  • Son locks sobre archivos, entre procesos (no entre threads de un mismo proceso).
  • Son advisory (consultivos): el kernel no los impone. Funcionan solo si todos los procesos cooperan y los consultan antes de tocar el recurso; uno que los ignore escribe el archivo igual.
  • Se aplican abriendo el archivo y usando fcntl(), flock() o lockf(). fcntl permite lockear rangos de bytes (un registro de tamaño fijo) sin bloquear el resto del archivo; flock/lockf son más simples pero no tienen rangos.

Locks en Rust (std::sync)

  • Mutex<T>: el caso exclusivo puro (equivale a un lock de escritura, o a un semáforo binario).
  • RwLock<T>: read() bloquea hasta obtener lock de lectura (puede haber otros lectores a la vez); write() bloquea hasta obtener el exclusivo (no puede haber ningún otro lock). La política concreta de prioridad la define el SO.
  • El lock envuelve el dato (Mutex<T>, no un mutex al lado de la variable): no hay forma de acceder al dato sin tomar el lock. Ahí está la diferencia de fondo con Unix.
  • Los traits Send/Sync validan en tiempo de compilación qué se puede mover o compartir entre hilos: para compartir T tiene que ser Send, y para permitir lectores concurrentes, Sync.
  • RAII: lock()/read()/write() devuelven un guard que libera el lock solo al salir de scope (trait Drop), o antes con drop() explícito. No existe el bug de «me olvidé el unlock()».
  • El patrón para mutar estado compartido entre hilos es Arc<Mutex<T>>: Arc comparte, Mutex serializa.
use std::sync::RwLock;
        let datos = RwLock::new(vec![1, 2, 3]);
        {
            let r1 = datos.read().unwrap();     // varios lectores a la vez
            let r2 = datos.read().unwrap();
            println!("{} {}", r1.len(), r2.len());
        }                                       // se liberan los guards de lectura (Drop)
        {
            let mut w = datos.write().unwrap(); // acceso exclusivo: ningún otro lock vivo
            w.push(4);
        }                                       // se libera el guard de escritura

Lock envenenado (poisoned)

Si un thread hace panic! mientras tiene el lock tomado, el dato protegido puede haber quedado a mitad de una modificación, o sea en un estado inconsistente. Rust marca ese lock como envenenado y todas las llamadas posteriores a lock()/read()/write() devuelven Err(PoisonError) en vez de entregar datos posiblemente corruptos.

  • Por qué existe: es una decisión de diseño para que un panic no se transforme silenciosamente en corrupción de datos. El lock te obliga a decidir qué hacer.
  • Es la razón por la que en todo el código de la materia se ve .lock().unwrap() o .expect(...): se está propagando ese posible envenenamiento.
  • Si sabés que el dato quedó consistente, se puede recuperar igual con into_inner() sobre el error.
Para no perder puntos: la diferencia conceptual de fondo no es la API, es que el lock de Unix es advisory (cooperativo: protege solo si todos lo consultan) mientras que el de Rust es estructural (el dato vive adentro del lock, no hay camino para saltearlo). Sumado a eso, el RAII del guard elimina la clase entera de bugs de «me olvidé el unlock()» y el poisoning convierte un panic con lock tomado en un error visible en vez de en datos corruptos. Ojo también con el self-deadlock: pedir write() teniendo vivo un read() en el mismo hilo traba el programa. Ver §11.

¿Qué modelos de concurrencia se ven? ¿Cómo se protege el estado compartido?

Los modelos: estado mutable/compartido (comparten variables → requiere sincronización explícita, el más propenso a races), fork-join (subtareas independientes en paralelo, sin estado compartido), canales/mensajes (se comunican enviando mensajes, sin memoria compartida; ej.: sockets), programación asincrónica (tareas livianas cooperativas, ceden en I/O) y actores (abstracción del pasaje de mensajes, estado privado). Para proteger el estado compartido se serializa el acceso: se marcan regiones (secciones críticas) que no pueden superponerse; si un procedimiento del conjunto se ejecuta, otro que quiera entrar debe esperar. Ver §4.

Fork-join: performance ideal y desventajas

Performance ideal: speedup lineal, t_secuencial / N_threads, siempre que las tareas estén balanceadas y el costo de sincronización/combinación sea despreciable. Desventajas: tareas desbalanceadas (unas tardan más), costo de sincronización/combinación en el join (esperar a que todas terminen), y que no todo problema es subdividible en tareas independientes. Ver §5.

Async: future, await, tarea, Pin y modelo «piñata»
  • Future: estructura que representa el resultado de un cómputo asincrónico que todavía no terminó pero estará disponible después.
  • async / await: async marca una función cuyo resultado es un future; await suspende la tarea hasta que el future esté listo sin bloquear el thread (devuelve el control al executor). block_on ejecuta un async de forma sincrónica bloqueando el thread (no usar dentro de async).
  • Tarea: unidad liviana de ejecución async administrada por el executor; puede suspenderse/reanudarse con await.
  • Pin: garantiza que un objeto no cambie de dirección en memoria; hace falta porque los futures pueden ser auto-referenciados y moverse invalidaría esas referencias.
  • Modelo piñata: la tarea se «abre» en cada await, se suspende y devuelve el control al executor, que intercala otras tareas; así se atienden muchas conexiones con pocos threads.

Cuándo usar async vs threads: async para muchas tareas I/O-bound con mucha espera (ej.: servidor web con miles de conexiones); threads para tareas CPU-bound que aprovechan varios núcleos (ej.: procesar imágenes). Ver §7.

Funciones de entrada y salida de una transición (Petri)

Para una transición t: sus lugares de entrada I(t) son los p con arco p→t, y sus lugares de salida O(t) los p' con arco t→p'. t está habilitada si cada entrada tiene M(p) ≥ W(p,t); al dispararse consume W(p,t) de cada entrada y produce W(t,p') en cada salida. Ver §14.

Ej 4 — Ambientes distribuidos

Tipos de eventos en un ambiente distribuido

La entidad es reactiva (solo responde a eventos externos): (1) llegada de un mensaje de otra entidad; (2) activación del reloj local (vencimiento de un temporizador propio); (3) impulso espontáneo (evento interno que la entidad genera sin estímulo externo, para iniciar actividad autónoma). Ver §19.

Algoritmo Ring de elección de líder (paso a paso)

Procesos ordenados lógicamente, cada uno conoce a su sucesor. Un proceso nota que el coordinador falló → arma ELECTION con su ID y lo manda al sucesor. Cada receptor agrega su ID y reenvía, hasta que el mensaje vuelve al iniciador. Éste lo cambia a COORDINATOR: el nuevo líder es el de mayor ID de la lista. Variante: propagar solo el ID más alto visto en vez de la lista completa. El COORDINATOR se saca de circulación al completar la vuelta. Diagrama en §17.

Costo y complejidad: distribuido vs centralizado

En distribuido se mide por: cantidad de mensajes M (transmisiones), la carga por entidad (acciones locales y su reparto) y el tiempo —distinguiendo el tiempo ideal (camino crítico bajo delays unitarios y relojes sincronizados) del tiempo real con delays arbitrarios—. Captura el costo dominante de la comunicación y los desbalances entre nodos. En centralizado la comunicación es por memoria compartida en una sola máquina, así que el costo se reduce a contar pasos de CPU y accesos a memoria (complejidad computacional local); no se cuentan latencias de red ni distribución de carga.

¿Cómo está compuesto el estado interno de una entidad y cómo se modifica?

El estado interno σ(x,t) es el contenido de los registros de x más el valor de su reloj c_x en el instante t. Se modifica solo por la ocurrencia de eventos, y es determinístico: si x recibe el mismo evento en dos ejecuciones y su estado interno es igual en ambas, el nuevo estado también será igual. Ver §19.

¿Qué es una entidad y qué capacidades tiene?

La entidad es la unidad de cómputo de un sistema distribuido: un proceso, hilo, actor, nodo o máquina. Es reactiva (solo responde a eventos). Capacidades: mantener un estado interno, procesar información localmente, recibir eventos externos, ejecutar acciones (atómicas) y comunicarse con otras entidades. Ver §19.

Acción, regla, comportamiento y conocimiento de una entidad
  • Acción: secuencia finita y atómica de operaciones (se ejecuta toda o nada).
  • Regla: indica cómo reacciona la entidad ante un evento externo según su estado interno (qué acción ejecutar).
  • Comportamiento: el conjunto de reglas; se lo llama también protocolo o algoritmo distribuido.
  • Conocimiento (local): el contenido de la memoria local y lo que se deriva; sin fallas no se pierde. Tipos: información métrica (mediciones de la red: nº de nodos, aristas), propiedades topológicas (forma del grafo: anillo, acíclico) y mapas topológicos (representación de quién está conectado con quién).
Restricciones temporales de los mensajes
  • Axioma de llegada: todo mensaje enviado, en algún momento llega.
  • Retardo finito: tarda un tiempo finito (la espera no es infinita).
  • Orientación local: la entidad distingue a quién envía y de quién recibe.
  • Delay acotado: existe un tope máximo de tiempo (permite definir timeouts).
  • Delay unitario: el tránsito de un mensaje se toma como una unidad de tiempo (para el «tiempo ideal»).

Ver §19.

Exclusión mutua distribuida: centralizado, distribuido y token ring (con problemas)
  • Centralizado: un proceso líder controla la SC; para entrar se le pide permiso y responde OK si está libre (si no, encola). Simple, pero es único punto de falla y cuello de botella. Conviene en sistemas chicos con servidor confiable.
  • Distribuido: sin líder; para entrar se pide permiso a todos; cada uno responde OK si no está ni quiere entrar, y si varios quieren, gana el de timestamp menor (Ricart-Agrawala). Sin SPOF, pero muchos mensajes y sensible a caídas. Conviene en P2P/sensores.
  • Token ring: los procesos forman un anillo y circula un token; solo quien lo tiene entra a la SC (no se puede acaparar). No hace falta saber quién está en la SC. Problema: si se pierde el token (proceso cae con él) hay que detectarlo y regenerarlo (timeouts/ping-pong). Conviene en redes estables e industriales.

Ver §17.

Algoritmos de elección de líder: Bully vs Ring

Asumen ID único conocido por todos. Bully: el que detecta la caída avisa solo a los de ID mayor; si alguno responde, ese sigue la elección (gana el de mayor ID); si nadie responde, se autoproclama y avisa a todos. Releva rápido al de mayor capacidad, pero manda muchos mensajes → conviene con jerarquía de nodos (datacenters, clusters). Ring: circula un ELECTION(ID) por el anillo acumulando IDs; al volver, el líder es el de mayor ID y se propaga COORDINATOR. Pocos mensajes → conviene en redes chicas y estables (sensores). Ver §17.

Transacciones: qué son, primitivas y propiedades ACID

Una transacción es una secuencia de operaciones que se ejecuta como una sola unidad lógica: todo o nada. Primitivas atómicas: BEGIN, END (intenta commit), ABORT (deshace), READ, WRITE. ACID: Atomicidad (todo o nada), Consistencia (deja el sistema en estado válido), Aislamiento (no interfiere con otras) y Durabilidad (una vez commiteado, permanece). Ver §15.

Algoritmos de implementación de transacciones
  • Private workspace: la transacción trabaja sobre una copia de los archivos; al commit se persiste, al abort se descarta. Simple, pero ocupa mucha memoria y no valida conflictos.
  • Write-ahead log (WAL): se opera in place pero se anota cada operación en un log antes de tocar el storage; para abortar se deshace leyendo el log de atrás hacia adelante.
  • Commit en dos fases (2PC): el coordinador manda PREPARE; los participantes votan READY; si todos, manda COMMIT. Ver el diseño de Ej 5 (conciertos).
  • 2PL (two-phase locking): fase de crecimiento (solo toma locks) y de decrecimiento (solo libera; no vuelve a tomar). Garantiza serialización pero puede dar deadlocks.
  • Concurrencia optimista: modifica sin locks y, al commitear, valida que nadie más tocó los mismos archivos; si hubo conflicto, aborta.
  • Timestamps: cada archivo tiene timestamp de lectura/escritura; la transacción recibe uno global y aborta si detecta un acceso «fuera de orden». Evita locks.

Ver §15.

Detección de deadlocks distribuidos: centralizado vs distribuido

En distribuido la detección es más difícil (latencias de red → falsos deadlocks). Centralizado: un líder recibe qué recursos tiene y espera cada proceso, arma un grafo de espera y si detecta un ciclo hay deadlock (simple, pero SPOF/cuello de botella). Distribuido (probe / Chandy-Misra-Haas): no hay grafo centralizado ni grafos locales acumulados. Cuando un proceso se bloquea, envía un probe message (con su propio ID como «origen») al proceso que tiene el recurso que necesita. Cada proceso que recibe el probe, si también está bloqueado, lo reenvía —actualizando emisor/destinatario— al proceso que tiene el recurso que él necesita. Si el probe vuelve al proceso que lo originó, se confirma que hay un ciclo → deadlock. Sin SPOF, pero cuesta más mensajes y más latencia para detectar el ciclo que en el esquema centralizado. Ver §16.

Control de concurrencia (2PL / timestamps / optimista): caso supermercado en hora pico

Inventario con alta contención (muchas transacciones sobre los mismos registros de stock):

AlgoritmoVentajaDesventaja en hora pico
2PLToma los locks de los productos antes de vender → garantiza consistencia del stock.Puede haber deadlocks entre vendedores que quieren los mismos productos.
TimestampsSin locks → sin deadlocks.Muchos aborts/retries y posible starvation con alta contención.
OptimistaExcelente con pocos conflictos y muchas lecturas.En hora pico → muchísimos aborts, se desperdicia trabajo, baja performance.

Recomendación: 2PL con prevención de deadlock (wait-die o wound-wait). Con mucha contención es preferible bloquear y esperar antes que abortar una y otra vez; minimiza aborts y mantiene el stock consistente. (Optimista convendría en un catálogo con muchas lecturas y pocas escrituras; timestamps, en sistemas distribuidos donde los locks son costosos.) Ver §15.

Pseudocódigo Rust (actores): resultado parcial de una elección en tiempo real

Las mesas emiten votos concurrentemente; un contador central agrega los parciales sin locks (cada actor procesa un mensaje a la vez).

use actix::prelude::*;
use std::collections::HashMap;

#[derive(Message)] #[rtype(result = "()")]
struct EmitirVoto { partido: String }

#[derive(Message)] #[rtype(result = "()")]
struct ContarBoletas { contador: Addr }

#[derive(Message)] #[rtype(result = "()")]
struct AgregarVotos { partido: String, votos: usize }

// Una mesa acumula sus boletas y, cuando se lo piden, manda su conteo parcial.
struct MesaActor { boletas: Vec }
impl Actor for MesaActor { type Context = Context; }

impl Handler for MesaActor {
    type Result = ();
    fn handle(&mut self, msg: EmitirVoto, _: &mut Context) {
        self.boletas.push(msg.partido);            // voto entrante (concurrente)
    }
}
impl Handler for MesaActor {
    type Result = ();
    fn handle(&mut self, msg: ContarBoletas, _: &mut Context) {
        let mut parcial: HashMap = HashMap::new();
        for p in &self.boletas { *parcial.entry(p.clone()).or_insert(0) += 1; }
        for (partido, votos) in parcial {
            msg.contador.do_send(AgregarVotos { partido, votos });
        }
    }
}

// El contador central agrega los parciales de todas las mesas (estado privado).
struct ContadorActor { votos: HashMap }
impl Actor for ContadorActor { type Context = Context; }

impl Handler for ContadorActor {
    type Result = ();
    fn handle(&mut self, msg: AgregarVotos, _: &mut Context) {
        *self.votos.entry(msg.partido).or_insert(0) += msg.votos;  // sin locks
    }
}

use std::sync::{Arc, Mutex};
use std::time::{Duration, Instant};

let links: Vec = /* 100 URLs */ vec![];
let n = 8;                                   // máximo de threads activos
let sem = Arc::new(Semaphore::new(n));       // limita la concurrencia
let total = Arc::new(Mutex::new(Duration::ZERO));
let mut handles = vec![];

for url in links {
    let sem = Arc::clone(&sem);
    let total = Arc::clone(&total);
    handles.push(std::thread::spawn(move || {
        let _permit = sem.access();          // no más de N a la vez (RAII)
        let t0 = Instant::now();
        // simular espera de red
        std::thread::sleep(Duration::from_millis(rand_ms()));
        let elapsed = t0.elapsed();

Compra de pasajes de micros de larga distancia (transaccionalidad)

Igual patrón que conciertos: para evitar reservar un asiento sin pagarlo (o venderlo dos veces) se usa 2PC. Coordinador: Sistema. Participantes: Inventario de asientos (disponible/reservado/vendido) y Pago.

  • El usuario elige fecha, origen y destino → el Sistema pide al Inventario los asientos libres.
  • Elige asiento → Inventario lo reserva con un TTL (transacción local) para que no lo tome otro mientras paga.
  • Al pagar arranca el 2PC: PREPARE a Inventario (¿sigue reservado y sin expirar? → VOTE_COMMIT) y a Pago (¿autoriza? → VOTE_COMMIT). Si ambos, COMMIT: asiento vendido + captura de fondos + emisión del pasaje.

Casos: éxito → ambos votan COMMIT y llega el pasaje. Falla (tarjeta rechazada o expiró la reserva) → Pago/Inventario vota ABORT y el asiento vuelve a disponible. Ver el esquema de conciertos (arriba) y §15.

[Diseño] Reserva de restaurantes con confirmación automática y timeout

El cliente elige restaurante, fecha, horario y nº de comensales; la reserva es «automática» y se confirma en a lo sumo 5 min, si no hay timeout.

  • Problemas de concurrencia: (1) dos usuarios reservan la última mesa a la vez → sobreventa/race; (2) la reserva queda «colgada» sin confirmar → hay que liberar por timeout; (3) cae el servidor que administra los locks/estado de las mesas → SPOF.
  • Solución: un actor por restaurante (o por mesa) que serializa las reservas (procesa un mensaje a la vez → sin race): al reservar marca la mesa reservada con un TTL y se auto-envía un Timeout; si vence antes de la confirmación, libera la mesa. Alternativa transaccional: 2PL/2PC sobre el registro de la mesa.
  • Casos: (1) dos por la última mesa → el actor atiende una y a la otra le responde «no disponible». (2) expira el timeout → la mesa vuelve a libre. (3) cae el servidor de locks → sin él nadie puede reservar; se mitiga con réplica/reelección de líder o reconstruyendo el estado desde un log.
