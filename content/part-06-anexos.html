Diseño de un sistema — Venta online con reserva de stock

Problema: tienda que despacha de un único depósito; los usuarios eligen producto/variante/cantidad, el sistema reserva temporalmente el stock, valida la cobertura de envío, cobra y emite la orden, evitando vender más unidades de las que hay incluso con muchos usuarios en simultáneo.

1) Esquema de transaccionalidad

El punto crítico es el decremento de stock: debe ser una sección crítica serializada por SKU. Un actor por producto (o un Mutex/lock pesimista por SKU) procesa las reservas de a una → imposible que dos usuarios reserven la última unidad (misma garantía que el invariante de los asientos en Petri). El checkout es una transacción con reserva de TTL: Reservar → ValidarEnvío → Cobrar → Confirmar, y si algún paso falla se hace rollback liberando la reserva.

Problema potencialCómo lo resuelve
Sobreventa de la misma unidadReserva serializada por SKU (actor/lock); solo se confirma si la reserva fue exitosa.
Cobertura de envío fallidaSe valida antes de cobrar; si falla, se libera la reserva.
Pago rechazadoRollback de la transacción: se libera el stock reservado (writeahead log / compensación).
Usuario que abandona el checkoutLa reserva tiene TTL: expira y el stock vuelve a estar disponible.

3) Casos de éxito y de falla

  • éxito Reserva OK → envío cubierto → pago aprobado → Confirmar: se descuenta el stock definitivamente y se emite la orden.
  • éxito Retiro en sucursal: igual pero sin validación de envío a domicilio.
  • falla Stock agotado por otro usuario durante el checkout: Reservar devuelve «Sin stock» → se avisa y no se cobra.
  • falla Pago rechazado: se envía Liberar al Producto y se cancela la transacción; el stock reservado vuelve.

5) Pseudocódigo Rust (actor Producto)

use actix::prelude::*;

#[derive(Message)]
#[rtype(result = "Result<(), &'static str>")]
struct Reservar { qty: u32 }

struct Producto { stock: u32, reservado: u32 }

impl Actor for Producto { type Context = Context; }

impl Handler for Producto {
    type Result = Result<(), &'static str>;
    fn handle(&mut self, msg: Reservar, _: &mut Context) -> Self::Result {
        // Un mensaje a la vez => decremento serializado, sin sobreventa
        if self.stock - self.reservado >= msg.qty {
            self.reservado += msg.qty;        // reserva temporal (con TTL aparte)
            Ok(())
        } else {
            Err("sin stock")                  // el checkout avisa al usuario
        }
    }
}

Ej 1 — Sección crítica y corrección

Definir el problema de la sección crítica: programa modelo y especificaciones de corrección

El programa modelo es el esquema abstracto de lo que hace cada proceso en un sistema concurrente que comparte recursos: un ciclo infinito cuyo código se divide en parte no-crítica (no toca recursos compartidos) y parte crítica o sección crítica (accede a recursos compartidos), separadas por un protocolo de entrada y uno de salida. La sección crítica debe progresar y finalizar eventualmente: nadie se queda adentro para siempre.

loop {
            seccion_no_critica();
            protocolo_de_entrada();   // sincronización
            SECCION_CRITICA();        // acceso al recurso compartido
            protocolo_de_salida();    // liberación
        }

Especificaciones de corrección — una solución correcta cumple estas tres:

  1. Exclusión mutua (safety): las instrucciones de la sección crítica no se intercalan. Si un proceso está adentro, ningún otro puede entrar.
  2. Ausencia de deadlock (safety, criterio de la cátedra): si dos procesos intentan entrar a la sección crítica, al menos uno lo logra. El sistema que todavía no terminó tiene que poder seguir avanzando productivamente.
  3. Ausencia de starvation (liveness): si un proceso intenta entrar, eventualmente lo consigue. Ninguno queda postergado para siempre.
Para no perder puntos: el fairness no es una especificación de corrección de la sección crítica. Fairness es una propiedad más general y más fuerte, sobre instrucciones: si una instrucción está continuamente habilitada, eventualmente debe ejecutarse. A la sección crítica solo le importa la garantía puntual y más débil de que el proceso que quiere entrar entre — y eso ya lo da la ausencia de starvation. Pedir fairness además sería redundante. Ver §10.
¿Cuál es la importancia de los criterios de corrección?

En concurrencia se pierde la garantía básica de la programación secuencial: misma entrada → misma salida. La salida depende del escenario de ejecución, o sea del interleaving que elige el scheduler, que puede cambiar entre corridas con la misma entrada. Por eso no alcanza con debuggear como en código determinístico: «anduvo bien en las pruebas» no prueba nada, porque el programa puede fallar 1 de cada 1000 veces y sin reproducirse. Los criterios de corrección dan propiedades demostrables para diseñar y validar algoritmos de sincronización, en lugar de depender del testing empírico.

Son de dos clases:

ClaseCuándo debe valerPropiedades
Safety (seguridad) Verdadera siempre, en todo interleaving posible: «algo malo nunca pasa». Exclusión mutua: dos procesos no deben intercalar ciertas subsecuencias de instrucciones (ej.: el acceso a una variable global compartida).
Ausencia de deadlock: un sistema que todavía no terminó debe poder seguir avanzando productivamente.
Liveness (vivacidad) Debe volverse verdadera eventualmente: «algo bueno en algún momento pasa». Ausencia de starvation: todo proceso listo para usar un recurso debe recibirlo eventualmente.
Fairness: si una instrucción está continuamente habilitada, eventualmente entra en el escenario de ejecución.

Por qué hacen falta las dos: solo con safety se puede tener un sistema «seguro» pero que no le sirve a nadie, con procesos postergados para siempre; solo con liveness se puede tener un sistema que progresa todo el tiempo pero produce resultados incorrectos, porque las races le corrompen los datos.

Para no perder puntos: la cátedra ubica la ausencia de deadlock dentro de safety, a diferencia de buena parte de la bibliografía, que la trata como liveness. El razonamiento: el deadlock es un estado inválido en sí mismo, no algo que «tarda en pasar». Ver §10.
¿Qué es un deadlock y qué consecuencias tiene? ¿Y en distribuido?

Dos o más procesos esperan por un recurso que el otro tiene, formando una dependencia cíclica: ninguno progresa, porque cada uno espera algo que el otro nunca va a liberar. Ejemplo clásico: P1 tiene el lock A y pide B; P2 tiene B y pide A.

Consecuencias:

  • La parte afectada del sistema deja de progresar: los procesos del ciclo quedan suspendidos para siempre.
  • Los recursos involucrados quedan inutilizables, retenidos y sin liberarse, bloqueando también a terceros que los necesiten.
  • El rendimiento global se degrada o se detiene, según qué tan críticos sean esos procesos.
  • Requiere intervención externa: el sistema no se recupera solo.

Complicaciones adicionales en distribuido:

  • No hay estado global observable. Un SO centralizado mantiene un grafo de asignación de recursos exacto; en distribuido cada proceso conoce solo su estado local y todo lo demás llega por mensajes con delay — o sea, toda información del resto es vieja por definición.
  • Mensajes desordenados → falsos deadlocks. Se puede detectar un ciclo que ya se resolvió, o no ver uno que existe. Se mitiga imponiendo orden causal con timestamps de Lamport.
  • La detección exige protocolos activos por mensajes: o un coordinador que mantiene el grafo global (simple, pero es un SPOF), o probe messages que se reenvían por la cadena de espera y, si vuelven al origen, delatan el ciclo (sin SPOF, pero más mensajes y latencia).
  • La resolución va por prevención con timestamps (wait-die, wound-wait) en vez de «elegir una víctima» local, para que todos los nodos decidan lo mismo sin consultarse.
  • Las fallas parciales son ambiguas: si un proceso no responde, no se puede distinguir si está caído, si se perdió el mensaje o si solo está lento.
Para no perder puntos: según el criterio de la cátedra el deadlock rompe safety, no liveness. Es un estado inválido terminal — en el momento en que se cierra el ciclo ya pasó algo malo y el sistema no puede salir nunca. No es «algo bueno que tarda en pasar»; eso sería la starvation, que sí es liveness. Ver §16.
Mecanismos de prevención de deadlocks en distribuido (a detalle)

Los dos mecanismos son Wait-Die y Wound-Wait. Ambos parten de lo mismo: cada transacción recibe al iniciar un timestamp único y global (Lamport), y timestamp menor = transacción más vieja. Cuando un proceso va a bloquearse por un recurso que otro tiene, se comparan los timestamps para decidir quién espera y quién aborta.

  • Wait-Die (no preemptive): si el que pide es más viejo, espera; si es más joven, aborta («muere») y reintenta más tarde con un timestamp nuevo. Nadie es abortado por otro: solo se auto-aborta el que pide.
  • Wound-Wait (preemptive): si el que pide es más viejo, aborta al que tiene el recurso («lo hiere») y se lo lleva; si es más joven, espera.

Por qué previenen el deadlock: los dos rompen la espera circular de Coffman forzando que las esperas vayan siempre en una única dirección del orden temporal. En Wait-Die solo un viejo puede esperar a un joven; en Wound-Wait solo un joven puede esperar a un viejo. Como los timestamps son un orden total y estricto, una cadena de esperas nunca puede volver a su origen: no hay ciclo posible.

SituaciónWait-DieWound-Wait
Pide el viejo, lo tiene el jovenEl viejo esperaEl joven aborta; el viejo lo toma
Pide el joven, lo tiene el viejoEl joven aborta y reintentaEl joven espera
TipoNo preemptive (solo auto-aborto)Preemptive (desalojo forzado)
Aborts y rollbacksMás: los jóvenes abortan seguidoMenos: las viejas quedan protegidas y progresan
Para no perder puntos: no confundir prevención de deadlock con exclusión mutua distribuida. La exclusión mutua (centralizado, Ricart-Agrawala, token ring) garantiza que entre un solo proceso a la vez a la sección crítica de un recurso. La prevención evita que se forme un ciclo cuando hay varios recursos y cada proceso pide más de uno. Son complementarias: podés tener bien resuelta la exclusión mutua de cada recurso y aun así trabarte en un ciclo global. Ver §16.
[Parcial] ¿Es busy-wait? Analizar fragmentos de código

Regla: es busy-wait (espera activa) si el loop espera por una condición chequeándola (polling), haya o no sleep; NO lo es si hace trabajo útil sin condición de espera, o si se bloquea hasta el evento. El sleep baja el CPU pero no cambia la naturaleza.

1C 2024 · Fragmento A — minero que produce lithium:

for _ in 0..MINERS {
    let lithium = Arc::clone(&mineral);
    thread::spawn(move || loop {
        let mined: u64 = rand::thread_rng().gen();
        *lithium.write().expect("failed to mine") += mined;   // trabajo útil INCONDICIONAL
        thread::sleep(Duration::from_millis((5000.0 * rng.gen::()) as u64));
    });
}
¿Es busy-wait?

NO. Cada vuelta produce (mina y escribe) sin esperar ninguna condición; el sleep es solo pacing.

1C 2024 · Fragmento B — produce una batería al juntar 100 de lithium:

for _ in 0..MINERS {
    let lithium = Arc::clone(&mineral);
    let baterias = Arc::clone(&resources);
    thread::spawn(move || loop {
        let mut lithium = lithium.write().expect("failed");
        if *lithium >= 100 {                       // <-- CONDICIÓN de espera
            *lithium -= 100;
            *baterias.write().expect("failed to produce") += 1;
        }
        thread::sleep(Duration::from_millis(500));
    });
}
¿Es busy-wait?

SÍ, espera activa «tibia». Cuando lithium < 100 no hace nada: poll-ea la condición «¿ya hay 100?» con un sleep. El sleep baja el CPU pero no lo vuelve espera pasiva. Correcto: una Condvar que despierte al hilo justo cuando el lithium llega a 100.

2C 2024 · Fragmento A — reintento de conexión:

loop {
    match TcpStream::connect("127.0.0.1:8080") {
        Ok(mut stream) => { stream.write_all(message.as_bytes()).expect("error"); }
        Err(_) => { thread::sleep(Duration::from_millis((5000.0 * rng.gen::()) as u64)); }
    }
}
¿Es busy-wait?

NO. Reintenta una operación externa (un server que puede estar caído) con backoff; no hay forma de «bloquearse hasta que el server levante».

2C 2024 · Fragmento B — procesa ACKs vencidos periódicamente:

loop {
    thread::sleep(Duration::from_millis(rng.gen()));
    let mut items = self.pending_acks.lock().unwrap();
    let now = Instant::now();
    let mut i = 0;
    while i < items.len() {
        if items[i].expiration <= now {
            if items[i].item_type == "ACK" {
                let _ = items.remove(i);
                drop(items);
                self.send_result_interfaces();     // TRABAJO real por pasada
                break;
            }
        } else { i += 1; }
    }
}
¿Es busy-wait?

NO (tarea periódica): cada pasada procesa los ítems vencidos; no se queda mirando una condición sin hacer nada.

Contraejemplo mínimo de busy-wait «caliente»: loop { if *flag.lock().unwrap() { break; } } — spin sin sleep ni trabajo, 100% CPU.

[Parcial] Identificar la estructura y sus errores (Mutex + Condvar)

Consigna: dado un struct { mutex: Mutex<i32>, cond_var: Condvar } con function_1 (si amount <= 0 hace wait, luego -= 1) y function_2 (+= 1 y notify_all): ¿qué estructura de sincronización es y qué error tiene?

Resolución

Qué es: un semáforo contador implementado como monitor (mutex + variable de condición). Sus dos variables internas se leen directo del código: mutex: Mutex<i32> es el contador V (recursos disponibles, no negativo) y la cola interna de la Condvar es el conjunto L de procesos bloqueados. function_1 es el wait() («obtener acceso») y function_2 es el signal() («liberar»).

Error 1 (el grave): usa if *amount <= 0 { wait } en vez de while. Condvar::wait() en Rust puede retornar aunque nadie haya hecho notify (spurious wakeup), y además notify_all despierta a varios waiters que compiten por el mismo recurso. Con if, el proceso chequea la condición una sola vez: si despierta con amount == 0 sigue de largo y hace *amount -= 1, rompiendo la invariante del semáforo (V ≥ 0) y dejando el contador en negativo. Solución: cambiar el if por while, para revalidar la condición en cada despertar.

Error 2 (el detalle que suma): notify_all() en function_2. Se incrementó en 1 solo recurso, así que solo un thread va a poder tomarlo: despertar a todos genera una estampida en la que N−1 revalidan la condición y se vuelven a dormir (trabajo desperdiciado y contención por el mutex). Corresponde notify_one(). Ojo: notify_all sí es necesario cuando los waiters esperan por condiciones distintas sobre la misma condvar.

(Ver §12.)

[Parcial] Revisión de código: productor-consumidor con buffer acotado 
const N: usize = 10;
let buffer = Arc::new(Mutex::new(Vec::::with_capacity(N)));
let buffer_local = buffer.clone();

Consigna: encontrar los problemas de concurrencia y explicar por qué es necesario el drop.

Resolución

(a) Problemas y solución:

  • Busy-wait (espera activa): ambos poll-ean con sleep(1s) en vez de bloquearse. Solución: una Condvar (o dos: notEmpty/notFull) que despierte al productor cuando hay hueco y al consumidor cuando hay ítem — o directamente un canal mpsc.
  • Duerme reteniendo el lock: en el else el sleep ocurre antes del drop, así que el hilo tiene el Mutex tomado durante todo el segundo → el otro hilo no puede entrar y el sistema se serializa/estanca. El drop debería ir antes del sleep.

(b) ¿Por qué el drop? El MutexGuard mantiene el lock tomado hasta que se destruye (RAII). Si no lo soltás antes de bloquearte/dormir, el otro hilo no puede adquirir el Mutex y nadie progresa. (Y acá está mal ubicado: soltar después del sleep no sirve.)

La solución correcta se modela en Petri como el productor-consumidor con buffer acotado (§14, Ej 2) — justo lo que pedía el Ej 4 del recuperatorio.

Comparar los efectos negativos: deadlock, race condition, starvation y busy-wait

Los cuatro se comparan encuadrándolos primero en las dos clases de propiedades de corrección: safety («algo malo nunca pasa») y liveness («algo bueno eventualmente pasa»).

EfectoQué esQué rompeEfecto en el programaCómo se corrige
Deadlock Un conjunto de procesos queda bloqueado indefinidamente, cada uno esperando un recurso que otro del conjunto tiene (P1 tiene A y espera B; P2 tiene B y espera A). Safety Terminal: ninguno de los involucrados progresa nunca más. Los recursos quedan inutilizables y hace falta intervención externa. Romper una de las 4 condiciones de Coffman (en la práctica, orden total de adquisición de recursos).
Race condition Dos o más procesos acceden a estado compartido sin sincronización y el resultado depende del interleaving. Safety (exclusión mutua) Bug intermitente y no reproducible: datos corruptos y resultados que cambian entre corridas. Casi invisible en testing. Serializar el acceso al estado compartido: lock, semáforo, monitor o actores.
Starvation Un proceso listo y esperando un recurso nunca lo obtiene porque otros lo acaparan, aunque el sistema en general avanza. Liveness Falla individual: ese proceso queda postergado para siempre; el resto funciona normalmente. Política fair: cola FIFO, envejecimiento, u orden por antigüedad (wait-die / wound-wait).
Busy-wait Un hilo pollea una condición en un loop para poder avanzar, en vez de bloquearse. El sleep baja el consumo pero no cambia la naturaleza. Nada: no rompe corrección, es un problema de eficiencia Quema CPU sin trabajo útil y degrada a los demás procesos, aunque la lógica de sincronización sea correcta. Bloquearse de verdad: semáforo o variable de condición, para que el SO despierte al hilo cuando ocurre el evento.
Para no perder puntos — deadlock vs starvation: en el deadlock nadie de los involucrados progresa nunca más; es un estado terminal, y por eso la cátedra clasifica la ausencia de deadlock como safety (nunca se debe llegar a ese estado), no como liveness. En la starvation el sistema sí progresa y solo un proceso puntual queda postergado: eso sí es liveness. Ver §10.
Las 4 condiciones de Coffman para que ocurra un deadlock

Un deadlock es posible solo si se cumplen las cuatro simultáneamente. Romper una sola alcanza para prevenirlo:

CondiciónQué significaCómo se rompeViabilidad
Exclusión mutua Un recurso solo puede estar en poder de un proceso a la vez. Permitir acceso simultáneo (ej.: lock de lectura compartido). No siempre posible: hay recursos que requieren acceso exclusivo por naturaleza.
Retención y espera (hold and wait) Un proceso retiene recursos mientras espera obtener otros. Pedir todos los recursos de una vez antes de empezar; si no están todos, no tomar ninguno. Restrictiva: obliga a saber de antemano qué se va a usar y aumenta la contención.
No apropiación (no preemption) Un recurso no puede arrebatarse por la fuerza; solo se libera voluntariamente. Permitir que el sistema le quite el recurso a un proceso. Factible con la CPU; difícil con I/O o transacciones a medio hacer.
Espera circular Hay un ciclo P1→P2→…→Pn→P1 donde cada uno espera un recurso que tiene el siguiente. Imponer un orden total de adquisición de recursos (siempre pedir A antes que B). La más usada: fácil de implementar y sin gran costo de rendimiento.

¿Qué es un semáforo? Operaciones y variables internas

Mecanismo de sincronización con dos variables internas: un entero no negativo V (contador de recursos disponibles, inicialmente k ≥ 0) y un conjunto/cola L de procesos bloqueados (inicialmente vacío). Modela N recursos idénticos accesibles a varios procesos concurrentemente. Ofrece dos operaciones atómicas (garantizadas por el SO):

  • wait(S) / P(S) / acquire: Si V > 0, decrementa V en 1 y el proceso continúa. Si V == 0, el proceso se bloquea y se agrega a L (el contador nunca queda negativo).
  • signal(S) / V(S) / release: Si L está vacío, incrementa V en 1. Si no, despierta a un proceso arbitrario de L (sin orden FIFO garantizado) y lo pone en estado ready (no incrementa V en este caso).

Pseudocódigo crudo:

// Semáforo: dos operaciones atómicas
        // Variables internas: V (int >= 0), L (conjunto de procesos bloqueados)

        fn wait(sem: &mut Semaphore) {
            if sem.V > 0 {
        sem.V -= 1;
            } else {
        // agregar proceso actual a L y bloquearse
        sem.L.push(current_process());
        block();
            }
        }

        fn signal(sem: &mut Semaphore) {
            if sem.L.is_empty() {
        sem.V += 1;
            } else {
        // despierta UN proceso arbitrario de L (no el primero necesariamente)
        let proc = sem.L.remove_arbitrary();
        ready(proc);
            }
        }

Variantes según V inicial:

  • Semáforo binario (V = 1): Solo permite un proceso a la vez; se comporta como un mutex. Evita race conditions en secciones críticas.
  • Semáforo contador (V = N): Permite a lo sumo N procesos accediendo simultáneamente (N recursos, ej. N conexiones de un pool, N lugares de estacionamiento).

Invariantes: V ≥ 0 siempre; V = k + #signal(S) − #wait(S) (donde k es el valor inicial).

Matiz crítico (para no perder puntos): signal despierta a un proceso arbitrario de L (el SO elige sin garantía de orden FIFO). Esto hace que un semáforo por sí solo NO garantiza ausencia de starvation; puede haber procesos que esperen indefinidamente mientras otros son despertados. Contrasta con signalC en monitores, que despierta al del tope del FIFO (orden determinista). Para starvation-freedom, hace falta implementación fair (como lectores-escritores con cola de turnos, §13).

Ver §12.

¿Qué es un mutex? Operaciones y diferencia con el semáforo

Garantiza exclusión mutua: un solo proceso accede a la sección crítica a la vez. Sus dos operaciones son lock() (toma el mutex, o bloquea al proceso hasta poder tomarlo) y unlock() (lo libera). Requiere soporte de hardware y del SO: instrucciones atómicas del tipo test-and-set.

En Rust, Mutex<T> envuelve el dato en vez de ser un lock suelto al lado; .lock() devuelve un MutexGuard<T> que libera solo al salir de scope (RAII), o antes con drop(). El patrón para mutar estado compartido entre hilos es Arc<Mutex<T>>.

Diferencia con el semáforo — la clave no es qué hacen sino quién puede operar:

MutexSemáforo binario
Quién liberaSolo el mismo thread que lo tomóCualquier thread puede hacer signal()
Simetríalock/unlock los usa el mismo hilowait/signal pueden ser hilos distintos
ExpresividadSolo exclusión mutuaModela una cantidad arbitraria de recursos
Qué representaUn dato concreto protegidoUn contador abstracto, sin dato asociado

El mutex tiene noción de dueño: es una llave que me llevo y devuelvo yo mismo. Rust lo impone a nivel de tipos — MutexGuard<T> no implementa Send, así que el compilador no te deja pasárselo a otro hilo para que lo libere. El semáforo, en cambio, sincroniza entre hilos distintos: uno hace wait() y otro hace el signal() que lo despierta.

Para no perder puntos: un semáforo binario y un mutex no son intercambiables, aunque los dos den exclusión mutua. Por eso productor-consumidor se resuelve con semáforos y no con un mutex: el consumidor se bloquea y lo tiene que despertar el productor, que es otro hilo, y signal() no necesita ningún «comprobante» previo — cualquiera lo llama, haya hecho wait() o no. Ver §11.
¿Qué es una barrera y qué operación tiene?

Coordina a un conjunto de N procesos/threads obligándolos a esperar en un punto hasta que todos lleguen. Tiene esencialmente una sola operación, wait(): el que llega se bloquea, y cuando llega el último se liberan todos y siguen. En Rust (std::sync::Barrier) es reutilizable: después de liberar a todos se reinicia para la ronda siguiente.

Su uso clásico es sincronizar por fases: que todos terminen una etapa antes de que cualquiera empiece la siguiente. Requiere que el trabajo se divida en rondas bien definidas, donde una fase depende de que la anterior la hayan completado todas las subtareas — simulaciones por pasos de tiempo, multiplicación de matrices por bloques, o el problema del banquero de la cátedra (una barrera para «todos listos para empezar la semana» antes de repartir, otra para «todos calcularon su parte» antes de permitir retiros).

wait() devuelve un BarrierWaitResult cuyo is_leader() da true solo para el último hilo que llegó. Tiene sentido: ese es el único que, al llegar, ya sabe que la condición de desbloqueo se cumplió, porque la completa su propia llegada. Sirve para que exactamente un hilo haga algo puntual después de la sincronización (loguear, consolidar el resultado) sin sincronización extra.

let barrier = Arc::new(Barrier::new(n));
        // ... en cada thread:
        let res = barrier.wait();      // bloquea hasta que lleguen los n
        if res.is_leader() {           // exactamente uno: el último en llegar
            consolidar_resultado();
        }
Para no perder puntos: no confundir el «líder» de una barrera con el de los algoritmos distribuidos (Bully, Ring). El de la barrera se redetermina en cada ciclo y no tiene ninguna responsabilidad más allá de la etiqueta; el líder distribuido tiene un rol activo y persistente (coordina, mantiene estado, se reelige si cae). Ver §12.
¿Qué es un monitor? Operaciones y de qué se compone

Herramienta de sincronización que encapsula estado + procedimientos + exclusión mutua. Lo central: solo un proceso ejecuta dentro del monitor a la vez, y esa exclusión mutua es implícita — la da la estructura, el programador no la escribe.

De qué se compone:

  • Nombre del monitor.
  • Variables internas: el estado compartido que protege.
  • Procedimientos que acceden a ese estado, y cuáles de ellos son la interfaz pública.
  • Inicialización de las variables internas.
  • Variables de condición: no guardan ningún valor, solo mantienen una cola FIFO de procesos bloqueados.

Operaciones (atómicas) sobre las variables de condición:

OperaciónQué hace
waitC(cond)Siempre bloquea: agrega el proceso al FIFO de esa condición y libera el lock del monitor para que otro pueda entrar. No evalúa nada.
signalC(cond)Despierta al del tope del FIFO. Si la cola está vacía no hace nada (la señal se pierde).
empty(cond)true si no hay nadie esperando en esa condición.

waitC siempre bloquea porque la variable de condición no tiene información propia para decidir (a diferencia del semáforo, que evalúa su contador). La condición real la evalúa el código del monitor en un while antes de llamarla:

monitor Buffer {
            items: Vec, count: usize, size: usize   // variables internas
            notFull: Condition, notEmpty: Condition      // variables de condición

            procedure insert(x) {                        // procedimiento público
        while count == size { waitC(notFull) }   // while, NUNCA if
        items.push(x); count += 1
        signalC(notEmpty)
            }
            procedure extract() -> i32 {
        while count == 0 { waitC(notEmpty) }
        count -= 1; let x = items.pop()
        signalC(notFull); return x
            }
        }

Tener más de una variable de condición sirve para separar las colas por motivo lógico: el productor espera por «no lleno» y el consumidor por «no vacío». Con una sola cola, un signalC podría despertar a otro consumidor que sigue sin poder avanzar.

Para no perder puntos: el docente penalizó como incompleta la respuesta «un monitor se implementa con un Mutex y una Condvar, y tiene wait y signal», con la marca «y todos sus procedimientos». Si te piden el monitor, describilo entero: variables internas, todos los procedimientos que exponen y protegen el estado, inicialización, variables de condición, y que la exclusión mutua es implícita. Ver §12.
Semáforo vs Monitor: similitudes, diferencias y cuándo usar cada uno

El semáforo es un contador entero no negativo con dos operaciones atómicas (wait/signal) y una cola de bloqueados. El monitor encapsula estado + procedimientos con exclusión mutua implícita (un solo proceso adentro a la vez) y usa variables de condición (FIFO de espera, sin valor propio).

Similitudes: los dos serializan el acceso a recursos compartidos, los dos bloquean de forma pasiva (nada de busy-wait), sus operaciones son atómicas, y cada uno se puede construir con el otro (un semáforo se implementa como monitor con Mutex<i32> + Condvar).

Diferencias en la semántica de las operaciones:

Semáforo (wait/signal)Monitor (waitC/signalC)
¿El wait bloquea?Puede o no: si V > 0 decrementa y siguewaitC siempre bloquea y libera el monitor
¿El signal tiene efecto?Siempre: incrementa o despierta a alguiensignalC no hace nada si la cola está vacía (la señal se pierde)
¿A quién despierta?A uno arbitrario de los bloqueadosAl del tope del FIFO
Tras la señalEl desbloqueado puede continuar inmediatamenteEl desbloqueado espera a que el señalizador deje el monitor

Diferencias de fondo:

  • Exclusión mutua explícita vs implícita: con semáforos la pone el programador, escribiendo wait/signal en el orden correcto; en el monitor la da la estructura y no se puede omitir.
  • Estado asociado: el semáforo es un contador abstracto sin datos protegidos (el buffer se protege aparte, con otro mutex); el monitor encapsula las variables internas junto con los procedimientos que las tocan, así que no hay forma de acceder al estado sin pasar por el protocolo.
  • Qué error habilita cada uno: con semáforos, olvidarse un signal → deadlock, e invertir wait/signal → se pierde la exclusión mutua. En el monitor esos errores no son expresables; el error típico es equivocar la condición del while de la variable de condición (y usar if en vez de while).

Cuándo usar cada uno: monitor si el recurso es complejo y tiene varias condiciones de sincronización (buffer acotado con notFull/notEmpty, cola de impresión); semáforo si solo hay que contar accesos a N recursos idénticos (N impresoras, conexiones de BD, lugares de estacionamiento).

Para no perder puntos: contestar dos o tres diferencias sueltas («el semáforo no tiene un recurso asociado», «su contador puede ser mayor que uno») se califica Regular. Hay que definir cada estructura y recién ahí comparar por ejes: semántica de las operaciones, quién garantiza la exclusión mutua, encapsulación del estado y riesgo de error. Ver §12.
Productor-consumidor con semáforos

Dos semáforos de conteo: notFull (espacios libres) inicializado en N, la capacidad del buffer, y notEmpty (ítems disponibles) inicializado en 0.

let not_full  = Semaphore::new(N);     // huecos libres
        let not_empty = Semaphore::new(0);     // ítems disponibles
        let buffer    = Mutex::new(VecDeque::new());

        // Productor
        loop {
            let item = producir();
            not_full.acquire();                        // espera si el buffer está lleno
            buffer.lock().unwrap().push_back(item);
            not_empty.release();                       // avisa: hay un ítem
        }

        // Consumidor
        loop {
            not_empty.acquire();                       // espera si el buffer está vacío
            let item = buffer.lock().unwrap().pop_front().unwrap();
            not_full.release();                        // avisa: se liberó un espacio
            consumir(item);
        }

Los semáforos son la herramienta natural acá porque el que hace wait y el que hace el signal que lo despierta son hilos distintos: el consumidor libera el espacio que destraba al productor. Un mutex no modela eso, porque solo lo libera quien lo tomó.

Los dos semáforos resuelven la sincronización productor↔consumidor, pero no la exclusión mutua dentro de cada familia:

  • 1 productor y 1 consumidor: el mutex del buffer no hace falta. Es la solución clásica de Ben-Ari con dos semáforos: nunca compiten por la misma posición.
  • Varios productores y/o consumidores: sí hace falta un mutex (o semáforo binario) envolviendo el acceso físico al buffer, para que dos productores —o dos consumidores— no se pisen entre sí.
Para no perder puntos: el wait del semáforo va primero y el lock del buffer después. Al revés (buffer.lock() y recién ahí not_full.acquire()) el hilo se bloquea esperando espacio con el buffer tomado, el otro no puede sacar nada para liberarlo, y es deadlock. Y ojo con el buffer: si se omite notFull y queda solo notEmpty, lo que modelaste es un buffer infinito — nunca preguntás si hay espacio. Ver §13.
Locks en Unix vs Rust, tipos y «lock envenenado»

Un lock implementa exclusión mutua con dos operaciones: lock() (el proceso se bloquea hasta poder obtenerlo) y unlock() (lo libera). Requiere soporte de hardware y del SO — instrucciones atómicas tipo test-and-set.

Los dos tipos son los mismos en ambos mundos: compartido (lectura, varios a la vez) y exclusivo (escritura, uno solo, bloquea a todos). Para tomar un compartido hay que esperar a que se liberen los exclusivos; para tomar un exclusivo, que se liberen todos, de los dos tipos.

Locks de UnixLocks de Rust (std::sync)
AlcanceEntre procesos, sobre archivos (o rangos de bytes)Entre threads del mismo proceso
Cómo se imponeAdvisory (consultivo): el kernel no lo fuerza; funciona solo si todos los procesos cooperan y lo consultanEstructural: el lock envuelve el dato (Mutex<T>), no hay forma de acceder sin tomarlo
Tiposshared / exclusiveRwLock<T> (read/write) y Mutex<T> (solo exclusivo)
Cómo se usanAbriendo el archivo y llamando a fcntl(), flock() o lockf().lock() / .read() / .write(), típicamente sobre Arc<Mutex<T>>

Lock envenenado (poisoned): si un thread hace panic! mientras tiene el lock tomado, el dato protegido puede haber quedado a mitad de una modificación, o sea inconsistente. Rust marca ese lock como envenenado y las llamadas posteriores a lock()/read()/write() devuelven Err, en vez de entregar datos posiblemente corruptos. Por eso en todo el código de la materia se ve .lock().unwrap(): está propagando ese posible envenenamiento. Existe para que un panic no se convierta silenciosamente en corrupción de datos.

Para no perder puntos: la diferencia de fondo no es la API sino que el lock de Unix es advisory (protege solo si todos lo consultan) y el de Rust es estructural (el dato vive adentro del lock). Ver §11.

Ej 2 — Modelos, fork-join y Redes de Petri

Red Ordinaria vs Red General de Petri

Una red de Petri es una herramienta gráfica y matemática para modelar y analizar sistemas concurrentes o distribuidos. Es un grafo dirigido bipartito con dos tipos de nodos: lugares (estados del sistema) y transiciones (eventos que provocan cambios de estado).

  • Red Ordinaria: PN = (T, P, A), donde T son las transiciones, P los lugares y A los arcos que conectan lugares con transiciones y viceversa. Todos los arcos tienen peso 1: cada disparo consume y produce exactamente un token por arco. Describe la topología del sistema.
  • Red General: PN = (T, P, A, W, M0). Extiende a la ordinaria agregando dos componentes a la tupla: W: A → N, la función de peso (cuántos tokens transporta cada arco), y M0: P → N ∪ {0}, la marca inicial (la configuración de tokens al arrancar).

Regla de disparo (general): t está habilitada si M(p) ≥ W(p,t) para todo lugar de entrada p; al dispararse consume W(p,t) tokens de cada entrada y produce W(t,p') en cada salida. La ordinaria es el caso particular con todos los pesos en 1.

Qué te permite modelar la general que la ordinaria no: los pesos dejan consumir o producir varios tokens de golpe y de forma atómica — «necesito K recursos a la vez» (un filósofo que toma sus dos palitos), o producción/consumo en lote.

Sobre M0: que sea parte formal de la tupla de la general y no de la ordinaria no significa que la ordinaria no tenga marcado inicial, sino que no es parte definitoria de su estructura. La ordinaria describe la arquitectura con independencia de en qué estado arranque; la general fija el punto de partida como parte de la definición.

Para no perder puntos: el docente marcó en rojo, en un final, «no explicás lo que es c/u, solo las diferencias». Definí cada red por separado —qué es una ordinaria, qué es una general— y recién ahí compará. Responder solo el delta pierde puntos. Ojo también con la redacción: se dice «todos sus arcos tienen peso 1», no «todos sus arcos es 1». Ver §14.

Fork-join, work stealing, y ¿por qué NO una única cola de tareas?

Fork-join: dividir recursivamente un cómputo grande en subtareas independientes, resolverlas en paralelo y combinar (join) los resultados. Las subtareas no necesitan bloquearse salvo para esperar la finalización de sus propias subtareas; pueden crearse en cualquier momento sin sincronización adicional.

Work stealing: algoritmo de scheduling para balanceo de carga. Cada hilo mantiene una cola de doble extremo (deque). Cuando genera subtareas las encola al final de su propia cola; cuando se queda sin trabajo, elige un hilo arbitrariamente y roba una tarea del inicio de su cola. Se roba del extremo opuesto porque el dueño y el ladrón trabajan en puntas distintas, minimizando la sincronización entre ellos.

Una única cola sería mala: la cola pasa a ser estado mutable compartido que requiere exclusión mutua; dos hilos competirían para tomar la misma tarea. Un hilo que genera muchas subtareas retiene el lock mientras las encola, haciendo esperar a todos los demás. Resultado: contención del lock, latencia, y la cola se vuelve cuello de botella, destruyendo el paralelismo. Ver §5.

(b) Lector-Escritor

Caso 1: Sin preferencia, N lectores conocido y acotado (técnica de pesos, sin inhibidores).

Un único lugar recurso con M0 = N tokens. Transición leer consume 1 token al empezar y lo devuelve al terminar → múltiples lectores concurrentes. Transición escribir consume los N tokens de golpe (arco de peso N) y los devuelve → impide dispararse si hay algún lector activo. No hay arco inhibidor: la exclusión sale del conteo de tokens.

Caso 2: Con preferencia de escritura, o sin conocer N de antemano (arco inhibidor obligatorio).

La preferencia de escritura exige frenar a los lectores mientras haya un escritor esperando. Un escritor que espera no consumió ningún token — el test de cero («no hay ningún lector activo») no se puede expresar contando tokens. Se usa arco inhibidor: la transición entrar lector solo dispara si el lugar de escritores esperando está vacío.

Matiz de la cátedra: el arco inhibidor es lo que le da Turing-completitud a Petri: es el único mecanismo que puede detectar un test de cero. Sin inhibidores (red ordinaria o general), la red solo puede preguntar «¿hay al menos K tokens?», nunca «¿está vacío?». Por eso no es posible modelar preferencia de escritura sin inhibidores, sea cual sea N.

¿Qué modelos de concurrencia se ven? ¿Cómo se protege el estado compartido?

Los modelos: estado mutable/compartido (comparten variables → requiere sincronización explícita, el más propenso a races), fork-join (subtareas independientes en paralelo, sin estado compartido), canales/mensajes (se comunican enviando mensajes, sin memoria compartida; ej.: sockets), programación asincrónica (tareas livianas cooperativas, ceden en I/O) y actores (abstracción del pasaje de mensajes, estado privado).

Protección del estado compartido: se serializa el acceso marcando secciones críticas (regiones de código que no pueden superponerse). Si un proceso está ejecutando la sección crítica, otro que quiera entrar debe esperar.

Fork-join: performance ideal y desventajas

Performance ideal: el tiempo para resolver el problema de forma secuencial dividido por el número de threads disponibles (speedup lineal). En la práctica no se alcanza por: desbalance de tareas (unas tardan más que otras, y el join espera a la más lenta) y costo de sincronización/combinación (procesamiento extra para unir los resultados parciales).

Ventajas: no hay condiciones de carrera porque las unidades de trabajo están aisladas; el resultado es siempre determinístico (no depende de las velocidades relativas de los threads); no hace falta compartir memoria entre threads.

Desventajas: exige que las tareas sean independientes (no sirve si hay estado compartido que serializar); el desbalance de carga reduce el speedup; el costo de sincronización en el join agrega latencia. Ver §5.

Async: future, await, tarea, Pin y modelo «piñata»
  • Future: estructura que representa el resultado de un cómputo asincrónico que todavía no terminó pero estará disponible después. Invocar una función async no ejecuta nada: solo crea el Future. La ejecución comienza cuando el executor hace el primer poll (o al hacer await).
  • poll: método que interroga un future para saber si terminó. Devuelve Poll::Ready(valor) si la operación completó, o Poll::Pending si no. Llamar a poll no garantiza progreso: puede retornar Pending porque el recurso aún no está listo.
  • Executor: la abstracción que implementa el runtime (Tokio, async-std). Es el encargado de hacer poll sobre los futures — no el thread principal. Traduce await en llamadas a poll y gestiona los hilos subyacentes.
  • async / await: async marca una función cuyo resultado es un future; await suspende la tarea hasta que el future esté listo sin bloquear el thread (devuelve el control al executor). block_on ejecuta un async de forma sincrónica bloqueando el thread (no usar dentro de async).
  • Tarea: unidad liviana de ejecución async administrada por el executor; puede suspenderse/reanudarse con await.
  • Pin: garantiza que un objeto no cambie de dirección en memoria; hace falta porque los futures pueden ser auto-referenciados y moverse invalidaría esas referencias.
  • Modelo piñata: es colaborativo, no preventivo. La tarea se «abre» en cada await, se suspende voluntariamente y devuelve el control al executor, que intercala otras tareas. Nadie interrumpe a la tarea por la fuerza: solo cede cuando llega a un punto await.

Cuándo usar async vs threads: async para muchas tareas I/O-bound con mucha espera (ej.: servidor web con miles de conexiones); threads para tareas CPU-bound que aprovechan varios núcleos (ej.: procesar imágenes). Ver §7.

Riesgo de starvation: el modelo piñata es cooperativo y no garantiza fairness. Una tarea CPU-bound que nunca llega a un await acapara el hilo del executor y mata de hambre a las otras. Por eso el cómputo pesado va en spawn_blocking, no en una tarea async común.
Funciones de entrada y salida de una transición (Petri)

Para una transición t: sus lugares de entrada I(t) son los p con arco p→t, y sus lugares de salida O(t) los p' con arco t→p'. t está habilitada si cada entrada tiene M(p) ≥ W(p,t); al dispararse consume W(p,t) de cada entrada y produce W(t,p') en cada salida. Ver §14.

Ej 4 — Ambientes distribuidos

Tipos de eventos en un ambiente distribuido

La entidad es reactiva (solo responde a eventos externos): (1) llegada de un mensaje de otra entidad; (2) activación del reloj local (vencimiento de un temporizador propio); (3) impulso espontáneo (evento interno que la entidad genera sin estímulo externo, para iniciar actividad autónoma). Ver §19.

Algoritmo Ring de elección de líder (paso a paso)

Procesos ordenados lógicamente, cada uno conoce a su sucesor. Un proceso nota que el coordinador falló → arma ELECTION con su ID y lo manda al sucesor. Cada receptor agrega su ID y reenvía, hasta que el mensaje vuelve al iniciador. Éste lo cambia a COORDINATOR: el nuevo líder es el de mayor ID de la lista. Variante: propagar solo el ID más alto visto en vez de la lista completa. El COORDINATOR se saca de circulación al completar la vuelta. Diagrama en §17.

Costo y complejidad: distribuido vs centralizado

En distribuido se mide por: cantidad de mensajes M (transmisiones), la carga por entidad (acciones locales y su reparto) y el tiempo —distinguiendo el tiempo ideal (camino crítico bajo delays unitarios y relojes sincronizados) del tiempo real con delays arbitrarios—. Captura el costo dominante de la comunicación y los desbalances entre nodos. En centralizado la comunicación es por memoria compartida en una sola máquina, así que el costo se reduce a contar pasos de CPU y accesos a memoria (complejidad computacional local); no se cuentan latencias de red ni distribución de carga.

¿Cómo está compuesto el estado interno de una entidad y cómo se modifica?

El estado interno σ(x,t) es el contenido de los registros de x más el valor de su reloj c_x en el instante t. Se modifica solo por la ocurrencia de eventos, y es determinístico: si x recibe el mismo evento en dos ejecuciones y su estado interno es igual en ambas, el nuevo estado también será igual. Ver §19.

¿Qué es una entidad y qué capacidades tiene?

La entidad es la unidad de cómputo de un sistema distribuido: un proceso, hilo, actor, nodo o máquina. Es reactiva (solo responde a eventos). Capacidades: mantener un estado interno, procesar información localmente, recibir eventos externos, ejecutar acciones (atómicas) y comunicarse con otras entidades. Ver §19.

Acción, regla, comportamiento y conocimiento de una entidad
  • Acción: secuencia finita y atómica de operaciones (se ejecuta toda o nada).
  • Regla: indica cómo reacciona la entidad ante un evento externo según su estado interno (qué acción ejecutar).
  • Comportamiento: el conjunto de reglas; se lo llama también protocolo o algoritmo distribuido.
  • Conocimiento (local): el contenido de la memoria local y lo que se deriva; sin fallas no se pierde. Tipos: información métrica (mediciones de la red: nº de nodos, aristas), propiedades topológicas (forma del grafo: anillo, acíclico) y mapas topológicos (representación de quién está conectado con quién).
Restricciones temporales de los mensajes
  • Axioma de llegada: todo mensaje enviado, en algún momento llega.
  • Retardo finito: tarda un tiempo finito (la espera no es infinita).
  • Orientación local: la entidad distingue a quién envía y de quién recibe.
  • Delay acotado: existe un tope máximo de tiempo (permite definir timeouts).
  • Delay unitario: el tránsito de un mensaje se toma como una unidad de tiempo (para el «tiempo ideal»).

Ver §19.

Exclusión mutua distribuida: centralizado, distribuido y token ring (con problemas)
  • Centralizado: un proceso líder controla la SC; para entrar se le pide permiso y responde OK si está libre (si no, encola). Simple, pero es único punto de falla y cuello de botella. Conviene en sistemas chicos con servidor confiable.
  • Distribuido: sin líder; para entrar se pide permiso a todos; cada uno responde OK si no está ni quiere entrar, y si varios quieren, gana el de timestamp menor (Ricart-Agrawala). Sin SPOF, pero muchos mensajes y sensible a caídas. Conviene en P2P/sensores.
  • Token ring: los procesos forman un anillo y circula un token; solo quien lo tiene entra a la SC (no se puede acaparar). No hace falta saber quién está en la SC. Problema: si se pierde el token (proceso cae con él) hay que detectarlo y regenerarlo (timeouts/ping-pong). Conviene en redes estables e industriales.

Ver §17.

Algoritmos de elección de líder: Bully vs Ring

Asumen ID único conocido por todos. Bully: el que detecta la caída avisa solo a los de ID mayor; si alguno responde, ese sigue la elección (gana el de mayor ID); si nadie responde, se autoproclama y avisa a todos. Releva rápido al de mayor capacidad, pero manda muchos mensajes → conviene con jerarquía de nodos (datacenters, clusters). Ring: circula un ELECTION(ID) por el anillo acumulando IDs; al volver, el líder es el de mayor ID y se propaga COORDINATOR. Pocos mensajes → conviene en redes chicas y estables (sensores). Ver §17.

Transacciones: qué son, primitivas y propiedades ACID

Una transacción es una secuencia de operaciones que se ejecuta como una sola unidad lógica: todo o nada. Primitivas atómicas: BEGIN, END (intenta commit), ABORT (deshace), READ, WRITE. ACID: Atomicidad (todo o nada), Consistencia (deja el sistema en estado válido), Aislamiento (no interfiere con otras) y Durabilidad (una vez commiteado, permanece). Ver §15.

Algoritmos de implementación de transacciones
  • Private workspace: la transacción trabaja sobre una copia de los archivos; al commit se persiste, al abort se descarta. Simple, pero ocupa mucha memoria y no valida conflictos.
  • Write-ahead log (WAL): se opera in place pero se anota cada operación en un log antes de tocar el storage; para abortar se deshace leyendo el log de atrás hacia adelante.
  • Commit en dos fases (2PC): el coordinador manda PREPARE; los participantes votan READY; si todos, manda COMMIT. Ver el diseño de Ej 5 (conciertos).
  • 2PL (two-phase locking): fase de crecimiento (solo toma locks) y de decrecimiento (solo libera; no vuelve a tomar). Garantiza serialización pero puede dar deadlocks.
  • Concurrencia optimista: modifica sin locks y, al commitear, valida que nadie más tocó los mismos archivos; si hubo conflicto, aborta.
  • Timestamps: cada archivo tiene timestamp de lectura/escritura; la transacción recibe uno global y aborta si detecta un acceso «fuera de orden». Evita locks.

Ver §15.

Detección de deadlocks distribuidos: centralizado vs distribuido

En distribuido la detección es más difícil (latencias de red → falsos deadlocks). Centralizado: un líder recibe qué recursos tiene y espera cada proceso, arma un grafo de espera y si detecta un ciclo hay deadlock (simple, pero SPOF/cuello de botella). Distribuido (probe / Chandy-Misra-Haas): no hay grafo centralizado ni grafos locales acumulados. Cuando un proceso se bloquea, envía un probe message (con su propio ID como «origen») al proceso que tiene el recurso que necesita. Cada proceso que recibe el probe, si también está bloqueado, lo reenvía —actualizando emisor/destinatario— al proceso que tiene el recurso que él necesita. Si el probe vuelve al proceso que lo originó, se confirma que hay un ciclo → deadlock. Sin SPOF, pero cuesta más mensajes y más latencia para detectar el ciclo que en el esquema centralizado. Ver §16.

Control de concurrencia (2PL / timestamps / optimista): caso supermercado en hora pico

Inventario con alta contención (muchas transacciones sobre los mismos registros de stock):

AlgoritmoVentajaDesventaja en hora pico

(Optimista convendría en un catálogo con muchas lecturas y pocas escrituras; timestamps, en sistemas distribuidos donde los locks son costosos.) Ver §15.

Pseudocódigo Rust (actores): resultado parcial de una elección en tiempo real

Las mesas emiten votos concurrentemente; un contador central agrega los parciales sin locks (cada actor procesa un mensaje a la vez).

use actix::prelude::*;
use std::collections::HashMap;

#[derive(Message)] #[rtype(result = "()")]
struct EmitirVoto { partido: String }

#[derive(Message)] #[rtype(result = "()")]
struct ContarBoletas { contador: Addr }

#[derive(Message)] #[rtype(result = "()")]
struct AgregarVotos { partido: String, votos: usize }

// Una mesa acumula sus boletas y, cuando se lo piden, manda su conteo parcial.
struct MesaActor { boletas: Vec }
impl Actor for MesaActor { type Context = Context; }

impl Handler for MesaActor {
    type Result = ();
    fn handle(&mut self, msg: EmitirVoto, _: &mut Context) {
        self.boletas.push(msg.partido);            // voto entrante (concurrente)
    }
}
impl Handler for MesaActor {
    type Result = ();
    fn handle(&mut self, msg: ContarBoletas, _: &mut Context) {
        let mut parcial: HashMap = HashMap::new();
        for p in &self.boletas { *parcial.entry(p.clone()).or_insert(0) += 1; }
        for (partido, votos) in parcial {
            msg.contador.do_send(AgregarVotos { partido, votos });
        }
    }
}

// El contador central agrega los parciales de todas las mesas (estado privado).
struct ContadorActor { votos: HashMap }
impl Actor for ContadorActor { type Context = Context; }

impl Handler for ContadorActor {
    type Result = ();
    fn handle(&mut self, msg: AgregarVotos, _: &mut Context) {
        *self.votos.entry(msg.partido).or_insert(0) += msg.votos;  // sin locks
    }
}

[Parcial] Pseudocódigo: descargar 100 links con máximo N threads y medir el promedio 
use std::sync::{Arc, Mutex};
use std::time::{Duration, Instant};

let links: Vec = /* 100 URLs */ vec![];
let n = 8;                                   // máximo de threads activos
let sem = Arc::new(Semaphore::new(n));       // limita la concurrencia
let total = Arc::new(Mutex::new(Duration::ZERO));
let mut handles = vec![];

for url in links {
    let sem = Arc::clone(&sem);
    let total = Arc::clone(&total);
    handles.push(std::thread::spawn(move || {
        let _permit = sem.access();          // no más de N a la vez (RAII)
        let t0 = Instant::now();
        // simular espera de red
        std::thread::sleep(Duration::from_millis(rand_ms()));
        let elapsed = t0.elapsed();
        *total.lock().unwrap() += elapsed;
    }));
}
for h in handles { h.join().unwrap(); }
let promedio = *total.lock().unwrap() / 100; // tiempo promedio

El semáforo acota los threads activos (baja latencia); el Arc<Mutex> acumula los tiempos. Como es I/O simulada, una variante idiomática sería async con un límite de concurrencia.

Compra de pasajes de micros de larga distancia (transaccionalidad)

Igual patrón que conciertos: para evitar reservar un asiento sin pagarlo (o venderlo dos veces) se usa 2PC. Coordinador: Sistema. Participantes: Inventario de asientos (disponible/reservado/vendido) y Pago.

  • El usuario elige fecha, origen y destino → el Sistema pide al Inventario los asientos libres.
  • Elige asiento → Inventario lo reserva con un TTL (transacción local) para que no lo tome otro mientras paga.
  • Al pagar arranca el 2PC: PREPARE a Inventario (¿sigue reservado y sin expirar? → VOTE_COMMIT) y a Pago (¿autoriza? → VOTE_COMMIT). Si ambos, COMMIT: asiento vendido + captura de fondos + emisión del pasaje.

Casos: éxito → ambos votan COMMIT y llega el pasaje. Falla (tarjeta rechazada o expiró la reserva) → Pago/Inventario vota ABORT y el asiento vuelve a disponible. Ver el esquema de conciertos (arriba) y §15.

[Diseño] Reserva de restaurantes con confirmación automática y timeout

El cliente elige restaurante, fecha, horario y nº de comensales; la reserva es «automática» y se confirma en a lo sumo 5 min, si no hay timeout.

  • Problemas de concurrencia: (1) dos usuarios reservan la última mesa a la vez → sobreventa/race; (2) la reserva queda «colgada» sin confirmar → hay que liberar por timeout; (3) cae el servidor que administra los locks/estado de las mesas → SPOF.
  • Solución: un actor por restaurante (o por mesa) que serializa las reservas (procesa un mensaje a la vez → sin race): al reservar marca la mesa reservada con un TTL y se auto-envía un Timeout; si vence antes de la confirmación, libera la mesa. Alternativa transaccional: 2PL/2PC sobre el registro de la mesa.
  • Casos: (1) dos por la última mesa → el actor atiende una y a la otra le responde «no disponible». (2) expira el timeout → la mesa vuelve a libre. (3) cae el servidor de locks → sin él nadie puede reservar; se mitiga con réplica/reelección de líder o reconstruyendo el estado desde un log.
